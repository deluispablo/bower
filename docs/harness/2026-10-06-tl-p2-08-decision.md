# Technical-lead decision TL-P2-2026-10-06-08

Lead: Claude `Planificador`. This answers two follow-ups that the `partial-pile-readiness` implementer raised through the coordinator. Adopted revision stays `2026-10-05-contracts-2`, and contract B is unchanged. The coordinator registers the entries.

## a. An unreadable declaration isolates only its pile

One declaration that cannot be read (a failed Drive read or a malformed record) must not break the whole Inbox listing. This applies the same isolation as the protected-prose review: one bad note never hides the others.

- **The affected pile** stays visible. It shows one plain sentence and a way to try again.
- **No fallback to an undeclared pile.** The pile is never treated as having no declaration, since that would let a run take it as an observed pile.
- **Runs leave it alone.** A run captures neither that pile nor its members; they stay in the Inbox untouched.
- **Logging.** The error is logged once to the console as a `BowerError`, not on every listing.

Register this as a defect entry with a failed-read test.

## b. A context the person edits is not an upload in transit

A pile's context note is the person's own words, and the person may edit them. The declaration already keeps the original words (`originalText`) for provenance. Readiness should only prove that the context arrived. It should not require the note to still match those original words forever.

- **The note is there.** The context note exists in the pile's folder, marked by its member key. Creating a text file in Drive is a single request, so the note is either complete or absent. Readiness then accepts it whatever its current text, because later changes are the person's edits. A run captures the current verified text; B already says "current context".
- **The person removed it through Bower.** A journaled Bin of the note, or clearing its text so the app bins it, means the person removed the context. The pile is ready with no context once its members are ready. If the pile has no members left, it is empty: the app offers to remove it, and no run ever counts it as filed.
- **The note is missing and the person never removed it.** Then the context has not arrived, and the app writes it again from the declaration's `originalText`. That retry needs no bytes from the person.
- **No pile is stuck for ever.** A pile set aside for its context, or for any reason, always shows the reason and an action: try again, or remove it.

Neither case adds a field to the declaration, so the existing guards stand. The implementer may add this to `partial-pile-readiness` if it fits there; otherwise register it as its own entry before P2-H.
