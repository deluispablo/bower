## Contract

1. **MOC regions (Q1).** A Bower-made MOC is Bower's note (`type: moc`, Bower's mark) with three new region kinds in `ownership-format.ts`: `moc-overview` (model-written), `moc-figures` and `moc-members` (script-written), each with its own mark. Old notes still parse. A MOC or hub without Bower's mark is never edited except by the existing link rewrite. No personal-edit handling for the new regions; Current state keeps its protections. No hierarchy creation (B1e).
2. **Selection reply (Q2).** A closed, validated step-1 shape `{ items: [{ itemId, kind, destination, wants }], asks }`: `kind` a type-row id or `unknown`; `destination` an existing folder id or `{ parentId, name }`; `wants` at most 5 note ids per source, only ids from the script-built candidate list. Step 2's allowed targets are exactly the chosen ids, the destination folder and its hub/MOC. Validation only here; the runner wiring is B1d.
3. **Retrieval state (Q4).** `.bower/retrieval.json`, versioned: by file id the path, version, summary and coverage, plus folder id, account and the changes cursor. `index.md` is a projection rebuilt from it. Both join RUNNER_WRITES explicitly; the app never writes either (hard rule; layout.ts). The cursor is written in the same artifact as the state that reflects it, in one write.
4. **`maintain` effect (Q5).** One deterministic manifest effect with declared inputs, evaluated from settled outcomes after the other effects and before the report barrier; idempotent (derived files rebuilt whole, log lines keyed by op id); never rows for refused effects; runs on every run when the feed has changes or effects settled; a done run does not re-run it. No new recovery engine: the existing manifest, checkpoint chain and write-once.
5. Every content write passes the modifiedTime it read; a read-to-act change is refused by the existing checks. One edit per file per run.
6. Compatibility rows for every src/data/contracts commit; old manifests, checkpoints and notes keep their meaning.
