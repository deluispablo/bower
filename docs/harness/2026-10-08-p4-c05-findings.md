# Coordinator findings: the TL-P4-11 and C05 batches (2026-10-08)

The owner asked for findings and errors to go to the lead so they get solved properly, not patched. This is what went wrong, the evidence, and a proposal for each.

## 1. Reviews keep finding the same kinds of defect

Since `6db97ce`, the Opus reviews reopened 7 entries. Several needed 2–3 rounds: `state-no-adoption` 3, and `admission-subrequest-budget`, `ask-one-per-thing`, `duplicate-by-hash`, `keep-one-note-merge` and `ask-answer-loop` 2 each. The mechanical worker stalled on `corpus-offer-real-pdf`, and it had to be escalated. The defects fall into four kinds:

- **Read, then act with no fence.** The duplicate's Bin did not recheck the twin or the copy. The keep-one-note Bin checked only name and place, so a person's edit made after the read was lost. Both are data loss. Both were caught in review, not by tests.
- **Matching by substring or name instead of identity.** Examples: `carriedLines` substring dedup, `mergesOf` name match, and a twin matched by name.
- **Copy that promises behaviour that isn't built.** "Doing it now" while the answer waits. "Next tidy-up" for "Write it", which no run ever did. The fallback line presented the person's own line as news.
- **Tests that do not pin the real case.** The `home-reads-once` scenario (7 → 6 calls) did not have the live shape. The first `home-inbox-first` red failed only because its hook was missing. The admission named test never reached the skip path.

**Proposal:**
- A packet checklist, stated up front in every packet:
  - every Bin, move or write passes the bytes, modifiedTime or md5 it read, with a test that changes the file between read and act;
  - match by id, never by name or substring;
  - every new sentence in the app is backed by a test of the behaviour it promises;
  - the red reproduces the live evidence, with numbers.
- Entries that bin, merge or move go to `bower-escalated` from the start.

## 2. Harness friction (mine and the workers')

- Workers sometimes deliver one commit, with no separate red. They also add tests whose names are not in the entry's verify, so `done.sh` reports that the verify passes without the change.
- When a later commit touched the same lines, I proved the red by hand and closed with `--known-green` 4 times.
- I added a verify that ran a `src` test through `runner`, so the check failed until I fixed the verify.

**Proposal:** the worker card must list the exact verify names. `check-harness` could reject a verify whose names exist in no test file (it does that already at check time; it could do it before merge).

## 3. Suite failures I caused

- **An orphaned dev server.** A P4-18 reviewer started vite on port 5191 in a worktree it later removed. The next full e2e reused it, and about 200 tests failed with `ERR_HTTP_RESPONSE_CODE_FAILURE`. I killed it and the rerun was green. Reviewers must not leave servers running. Proposal: reviewers never run e2e, or must stop what they start.
- **A fixture change not suite-tested before merge.** The grounded hub line (`437229a`) changed demo text that `capabilities-b` C06 still expected. I merged it after only the worker's partial e2e. A later worker found and fixed it. Proposal: a full `e2e:fake` before merging any change to corpus, demo or fake fixtures.

- **Home.**
  - Live, the Inbox took about 45 s, behind the report. On the latency fake that is now 0.6 s.
  - The full read is still about 6 s, because `loadReport`'s `refreshFolder()` clears the read cache mid-`piles()` (confirmed, not fixed).
  - The Tidy up count comes from the listing and can drop once readiness is known.

Proposal: the scorer checks that every number in `expected.json` is grounded in the case's own files, the same rule as `numbers-grounded`.

Some touch data or honesty: a refused Bin still closes the hash question; a held pile counts against the quota until the P4-E refund; disagreeing answers; KEEP_CHANGED wording. Proposal: a polish batch before C06, prioritised by data safety and honesty.
