## Findings

### Important — define noncircular publication authority for a loose single file

Proposal line15 requires a confirmed/reconciled declaration **and actual container/file anchor before member dispatch**. Line17 also preserves a single file without a pile folder and requires discovery before that file exists. In the loose-file layout, the file can itself be the proposed anchor. If that is the intended binding, requiring its confirmed ID before its own upload is circular. Current `DriveVault.addPile:415–456` uses the existing Inbox as parent for a lone file; `sendAll:718–769` creates its member using DriveApi.upload/createText. The inspected DriveApi has no general binary update into a precreated empty placeholder. Blind placeholder/recreation or a mandatory new pile folder would change the proposed interface/layout and is not already authorized.

This is a design-blocking ambiguity in the predispatch rule, distinct from the declared R4 uncertainty after dispatch. An existing Inbox parent could be the intended placement authority, but the text must explicitly say that rather than imply a pile-file ID already exists. Recommendation: for loose input, let the confirmed immutable declaration plus authenticated root/Inbox parent and stable member/create-intent key authorize its single initial create; bind the returned unique in-scope file ID only after reconciliation. For a real pile folder, require its reconciled container before child creation. Keep the existing no-folder visible layout and pending discovery from the declaration. The technical lead must approve the exact authority/order and unknown-create handling; this review adopts no fields or helper API. Add a deterministic lone-file before-effect/unknown-effect fixture, alongside folder and note-only controls, before producer activation. If a different compatible anchor protocol is intended, specify it explicitly and account for required API changes as separate prerequisites.

### Minor — narrow the claim about already implemented device-byte cleanup

Proposal line21 says quota/denial/eviction/sign-out clears device bytes “as already implemented”; fixture row58 combines those storage events with S02 memory clearing. Current `src/data/device.ts:27–37` clears the in-memory holder when forgetThisPerson is invoked, including when Storage then refuses access. `src/data/draft-files.ts:7–23` is a Map; it contains no durable Blob store or quota/eviction listener. `Add.tsx:53–81` deliberately retains current-page state after metadata Storage denial; such denial alone does not invoke person cleanup. Approved D02 explicitly keeps durable retained bytes/reselection implementation pending. Remote missing-member discovery is also proposed, not current behavior.

Recommendation: say that S02 already clears retrievable current-page references on central person cleanup, even if storage is blocked. Separately state future best-effort retention/quota/denial/eviction behavior: unavailable bytes require visible content-verified reselection while the adopted remote declaration keeps expected members discoverable. Split row58's storage-loss case from sign-out cleanup so neither is reported as current S02 proof. This is a prose/evidence repair, not an instruction to implement a durable store or repeat owner policy approval.

Confirm existing originating-uploader retry versus fresh-client missing bytes, hash-verified reselection, size/identity mismatch refusal, quota/denial/eviction, sign-out scope and R4 completion proof. Already approved D02 needs technical implementation decisions, not another owner policy vote.
