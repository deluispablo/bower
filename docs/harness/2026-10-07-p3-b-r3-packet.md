# Packet: r3-executor-probe (P3-B)

Starting model: `bower-evaluator` (Sonnet). Reason: a bounded measurement of how GitHub Actions starts runs, with no Bower code involved ([TL-P3-12](2026-10-07-tl-p3-12-r3-r4-and-p3-6-close.md), R3 and its amendment).

- **Where:** the instance repository named in your prompt only. Never write its name into a file, commit or report line; call it `INSTANCE`. Its workflow `.github/workflows/probe.yml` (instance commit `cca496b`) listens only to `repository_dispatch` type `bower-probe`. Read it first with `gh api` (contents, read-only) and confirm three things before any dispatch:
  - it uses no secrets, model or Drive;
  - its `run-name` is the request id;
  - its concurrency group is per run id, with no `cancel-in-progress`.
  On any surprise, stop.
- **Never:** dispatch any other event type, touch other workflows, variables or secrets, push, or re-run or cancel runs. Use only `gh api` against `INSTANCE`.
- **Dispatch:**
  ```bash
  gh api repos/INSTANCE/dispatches -f event_type=bower-probe -f 'client_payload[run_id]=…' -f 'client_payload[request_id]=…'
  ```
  The ids are synthetic: lowercase letters, digits and dashes only, for example `r3-run-1`, `r3-req-1a`.
- **Observe:** `gh api repos/INSTANCE/actions/runs?event=repository_dispatch` (filter by `name`/`display_title` equal to the request id). Read the run's `created_at`, `run_started_at` and `updated_at`, its status and conclusion, and its artifacts (`/actions/runs/{id}/artifacts`, then download `probe-report` and read `report.json`). Poll no faster than every 5 s.
- **Bounds:** 8 dispatches and 30 minutes in total. Stop on a missing permission, an unexpected action or a passed bound. Report it, never retry.

## Steps

1. **Three serial baselines** (3 dispatches). For each, record the times from dispatch (your clock, at the 204) to run created, started and completed. A 204 with no run found is "accepted, not observed", never a pass.
2. **Two same-run duplicates** (2 dispatches, same `run_id`, different `request_id`, sent back to back). Record whether both start, one queues behind the other, or one is cancelled.
3. **Lost dispatch reply** (1 dispatch). Send it but treat the 204 as unknown. Before any redispatch, find the run by its `run-name` (the request id). Record that exactly one logical run exists. Do not redispatch if it is found.
4. **Lost completion** (uses the step-3 run, no new dispatch). There is no callback. Reconcile from the run's `conclusion` plus its `probe-report` artifact (`report.json` names the run id and attempt). A run with no artifact is never called done.

Up to 2 dispatches stay unused as a margin. They are not repurposed.

**Return, under 20 lines:**
- the workflow checks;
- a table per dispatch: step, dispatch → created → started → completed in seconds, conclusion, and whether an artifact exists;
- the range (min to max) of each interval, with no percentiles;
- the duplicate behaviour seen;
- the lost-reply and lost-completion outcomes;
- totals: dispatches and minutes;
- findings.
