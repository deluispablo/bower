**4. Root cause and options**

The primary defect is **report access coupled to replay eligibility**, compounded by **generic request completion copy independent of settlement outcome**. `RunLinks` already supports the required row; report generation is not the demonstrated failure.

Standard pattern, cited offline: make task outcomes visible ([Nielsen’s visibility of system status](https://www.nngroup.com/articles/ten-usability-heuristics/)) and provide a real link to details ([WAI-ARIA link pattern](https://www.w3.org/WAI/ARIA/apg/patterns/link/)). The existing renderer already cites that link/list pattern at [RunLinks.tsx:9](/Users/deluisp/Projects/bower-app/src/features/tidy/RunLinks.tsx:9).

- **(a) Expose completed reports independently of replay.** Home offers the instructions result; an explicit “view result” action opens the finished sheet; reuse `RunLinks`. Keep replay rules intact. Risk: acknowledgement, focus and confirmation semantics need care; generic Bower copy remains.
- **(b) Persist the request’s actual settlement explanation in `done`.** Derive it from `settleRequest`’s rows by request ID, using the existing completion field and note-link renderer. Risk: historical completion strings remain generic, and Home/status report access remains broken.
- **(c) Combine (a) and (b), recommended.** Make the explanation visible beside the request and retain access to the shared report. Risk: broader UI scope, requiring lead/designer ruling. Reuse settlement and `RunLinks`; do not add another outcome policy or infer request identity from equal text.
