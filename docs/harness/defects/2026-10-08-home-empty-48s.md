# home-empty-48s: an empty Inbox says "Looking…" for 48 s

Diagnoser note (TL-P4-15), 2026-10-08, on `claude/p3` 0173605 (staging 45e9742, same code). Read-only; no code changed.

## What failed

Staging, real Drive, account A, empty Inbox, fresh load after Use here: "Inbox / Looking…" for ~48 s, then "Nothing waiting". 126 Drive calls: 5 listing queries sent twice in parallel (done by 3 s); 59 `alt=media` reads one at a time (~700 ms each) to 44 s; 56 in parallel at ~45 s; 113 distinct files (log line in `DEFECT_LOG.md`).

Reproduced on the pretend Drive (scratch test, not committed): empty Inbox plus N old `declaration-*.json` in `.bower/piles`, 100 ms a call, 4 at once. `piles()` made N reads, never more than one at a time: N=5 took 0.56 s, N=20 took 2.1 s. A `refresh()` during the first `piles()` made 2 `listAll`. `home-cache.test.ts` still passes (4/4).

## Why (5 whys)

1. **Why "Looking…" with nothing in the Inbox?** The status line and the Tidy up button wait for the full `piles()` read, even when the listing shows no pile (`Home.tsx:48`, `:167`). The Questions panel waits too: `questions()` awaits `piles()` (`drive-vault.ts:1288`).
2. **Why does `piles()` take ~45 s with no pile?** It always ends with `looseMissing` (`drive-vault.ts:655`, `:705`). That calls `findLooseDeclarations`, which reads every `declaration-*.json` in `.bower/piles` that no live pile carries. With an empty Inbox, no pile is live, so it reads every declaration ever written. It reads them in a `for` loop with `await read()` (`pile-readiness.ts:189-198`), so the reads go one after another: ~53 × ~700 ms. For each declaration it finds to be loose, `accountPile` then reads every disposition ever written (`readDispositions`, `pile-readiness.ts:300-315`, `Promise.all`) only to learn that a past run consumed it. That is the burst of 56 at ~45 s. Count: 4 Bower files + 53 declarations + 56 dispositions = 113. The exact split is inferred, not checked against the live folder.
3. **Why must it read them all?** A declaration's name carries only its id and hash (`layout.ts:30`). Whether it is loose or a folder, which pile it belongs to, and whether a run consumed it are known only from its bytes and from the bytes of every disposition. Nothing retires a declaration or disposition once a run consumes it: no Bin call in `src/data/spine/`. So "loose things that never arrived" is computed from the whole history of `.bower/piles`, not from the current Inbox.
4. **Why did the fakes not show it?** `live-shape.ts` adds one *live* declared pile, which the loose scan skips, plus 20 dispositions (`:24`). It adds no declarations left over from filed piles, so the serial loop never runs. The golden says so: `readBytes: 21` = 1 declaration + 20 dispositions (`home-cache.test.ts:81`). The test also lists the folder before measuring (`:33`), which hides the double listing, and it times `pilesListed()`/`piles()`, never the empty-Inbox "Looking…". TL-P4-13 addendum 2 accepted ~4 s because "the full read is not what the person waits on". On Home's status line, the person does wait on it.
5. **Design cause:** readiness is derived by reading the whole history of `.bower/piles` (TL-P2-21/29/31: "found by real parents"), and nothing bounds that set to the piles in the Inbox now. `home-reads-bounded` (TL-P4-13 add. 2) bounds dispositions and changes but **not declarations**. After it, an empty Inbox would still read every old declaration, one at a time.

**Side causes.** *Listings twice:* `refresh()` sets `ix = null` and starts a new `listAll`, dropping a listing already on its way (`drive-vault.ts:214-216`). On load, `LiveRuns.loadReport` → `refreshFolder` (`runs.ts:301`, `:233`) for an unseen finished run, and/or Use here's `activeHere('take')` (`live/index.ts:470`), lands during Home's first `index()`. Which of the two fired on staging is unverified. *questions.json and suggestions.json twice:* `json()` reads Bower's files with `keep=false` (`drive-vault.ts:1388`), and the refresh's emit makes every hook ask again. *Unverified:* the log line says Rules.md was read twice, but `text()` keeps it by modifiedTime. The code issues questions.json, suggestions.json and Rules.md concurrently, so I cannot explain them appearing serial without the HAR.

## Owner mechanism

**None on the map** for the main cause: the pile readiness accounting (`src/data/pile-readiness.ts`, the one rule the Inbox and the runner share). The lead should add it. The double listing belongs to **Drive read cache** (`src/data/drive/`, target `c2-read-cache`: "only the listing is ever invalidated").

## Same class elsewhere (7)

1. `pile-readiness.ts:189-198`: serial reads, O(history). Also called by `drive-vault.ts:694` (`looseDeclarationOf`, on Remove/Undo, with no skip set, so it reads even live declarations).
2. `pile-readiness.ts:300-315`: every disposition for each `accountPile`. Callers: `drive-vault.ts:730`, `:756`, `:791`; `spine/plan.ts:221`, `:296`.
3. `spine/read.ts:108-110`: Worker admission reads ahead every disposition once any pile is declared. That is O(history) against the subrequest budget (TL-P4-11).
4. `pile-readiness.ts:142-149`: `findDeclaration` reads copies one at a time (bounded by copies; minor).
5. `drive-vault.ts:214-216`: `refresh()` drops a listing already on its way. Callers: `runs.ts:233`, `live/index.ts:470`.
6. `drive-vault.ts:1388`: Bower's files are read again on every ask (`keep=false`).
7. `drive-vault.ts:1288`: `questions()` waits for the full `piles()`.

## Options

- **(a) Fix in the owner. Size M, risk medium.** Widen `home-reads-bounded` to declarations. `declare()` (`drive-vault.ts:~928`) stamps each declaration's `appProperties` with its pile id and anchor kind, using the existing `PROP`. The runner stamps dispositions with the pile id, as already ruled. `findLooseDeclarations` and `readDispositions` then pick files from the listing, which already returns `appProperties` (`drive-http.ts:14`), and read only the loose, unconsumed ones. Older unstamped files are read through the existing `limiter(READ_AHEAD)` (`spine/read.ts:64`) instead of one at a time. `refresh()` joins a listing that started after the event it refreshes for (`index()`). Risk: a contract change shared with the runner (`c1-shared-contracts`). Old folders still read their unstamped history once per load, but in parallel.
- **(b) Refactor first, then fix. Size L, risk low per step.** Build `c2-read-cache` first (one cache, a single-flight listing, so 5 and 6 disappear). Then give `pile-readiness.ts` one "pile records for these piles" query used by the Inbox, Remove, admission (`spine/read.ts`) and the plan (items 1-3). Then (a) becomes a change in that one function. This matches TL-P4-14 stage 2, but staging stays slow until then.
- **(c) New mechanism. Not needed.** A device cache was rejected (TL-P4-13 add. 2). A Worker-side pile index would be a second source of readiness. Binning consumed records would remove the audit trail for recovery.

## Regression test (class)

"Home makes the same Drive calls, and the Inbox is ready within one listing plus one read wave, after 10 and after 500 earlier runs." It runs on the latency fake with leftover **declarations** (loose and folder) and dispositions of filed piles, an empty Inbox and a cold listing (no warm-up `tree()`), and with an unseen finished run, so the report's refresh overlaps the first load. It asserts: `listAll` = 1; reads independent of N; at most one sequential wait per kind of record; and Home's Inbox leaves "Looking…" within that bound. Add the leftovers to `live-shape.ts` so the 46-call golden covers them.

## Ruling: TL-P4-16

Option (b), per [TL-P4-16](../2026-10-08-tl-p4-16-baseline-defects.md): `c2-pile-records` replaces `home-reads-bounded` in stage 2, right after `c2-read-cache`. One pile-records query; declarations and dispositions stamped with their pile id; `questions()` no longer waits for `piles()`; `live-shape.ts` gains leftover declarations.
