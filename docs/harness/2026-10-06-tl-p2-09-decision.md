# Technical-lead decision TL-P2-2026-10-06-09

Lead: Claude `Planificador`. This answers the coordinator's question from the `partial-pile-readiness` review (I1, third point). Adopted revision stays `2026-10-05-contracts-2`, and contract B is unchanged.

## The question

Sometimes a run files a declared pile's members but keeps the pile folder, because the Bin guard found a child added late. A fresh client then has to tell which declared members are already filed and which are still missing. On the legacy path there is no consumed disposition to tell it.

## Ruling: hash-verified lookup for readiness, and the disposition once B exists

- **On both paths, readiness looks the members up.** A declared member whose file carries the same `bowerItem` (member key) and is found outside the pile folder, not in the Bin, with the declared size and sha256, has arrived and has left the pile. The pile does not wait for it, never lists it as "Didn't arrive", and no run files it again.
  - **Where to look.** The lookup uses the vault index Bower already lists. It needs no new Drive query.
  - **Where the hash comes from.** In P2 it is the fake-stored evidence. In P3 it is Drive's own checksum metadata.
  - **A failed hash check is not "filed".** A file with that key but a different size or hash is a `conflict` observation, shown to the person. It is never trusted as filed.
  - **What this proves.** This is a readiness fact, not a claim of consumption. It never writes or replaces a disposition.
- **On the B path, the runner also writes the consumed disposition** for the members it filed, under guard 13 (option A). The disposition is then the authoritative record. The lookup stays as the readiness view for legacy runs and for members moved outside a run.
- **Rejected: C, holding the whole pile on the legacy path.** It does not remove the case: a child can still arrive between the moves and the Bin. It would also block a whole pile on one rare late addition. The lookup is just as simple and covers both paths.

What is left of the pile (the late child, plus the context note if it is still there) is an ordinary pile for the next run. Its context still applies, because the person added the late child to that pile.

The coordinator's I3 fix is accepted: the pretend snapshot keeps size and sha256 for files too large to keep their bytes, as fake-stored evidence, serialized with `upload-queue-persistent`. Folding `declared-pile-context-arrival` into `partial-pile-readiness` is accepted too.
