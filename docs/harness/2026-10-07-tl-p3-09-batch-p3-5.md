**Coordinator question, 2026-10-07:** the R2 probe needs `POST /vault` and `GET /drive/token`, which do not exist yet. Should R2 be split, or should those two entries be built first?

**Ruling: build them first (the coordinator's option 2).** The owner then signs in once per account, in one session that runs all of R2: identity isolation and folder and Drive visibility.

- **Batch P3-5:** `worker-drive-token` and `worker-vault-pointer`, both on `bower-implementer` (Sonnet), stub-first, with one Opus review (TL-P2-46 until Codex returns).
  - **`worker-drive-token`:** refreshes with the encrypted refresh token held in the person object, returns `{ accessToken, expiresAt }` (at most 1 h), and honours `?fresh=1`. It answers 409 `no-folder` before a folder exists.
  - **`worker-vault-pointer`:** answers `{ folderId, found }`. It finds an existing Bower folder or makes one from the template. It never deletes, and it stores only the pointer, never content.
  - **Also in the batch:** the allowlist check on each session (TL-P3-06 note) and the stale-epoch headers already in CORS.
- **Until then, no owner sign-in.** The lead checks the Google wiring without signing in: `/health` is green, and `/auth/login` redirects to Google with the staging `redirect_uri` and the owner's client.
- **After P3-5 is deployed,** one owner session runs R2 in full (R2a identity and R2b folders), driven by `bower-evaluator` as agreed. `drive-real-behavior-suite` follows on the second account's synthetic folder.

## Amendment: the vault-pointer fix round (I1, I2)

Use both mechanisms; they guard different failures.

- **Two calls at once (I2): the person object.** Folder creation runs inside the person's Durable Object, one at a time, so a second simultaneous call waits and then finds the first folder ([Durable Objects: in-memory state and input gates](https://developers.cloudflare.com/durable-objects/reference/in-memory-state/)).
- **A lost reply (I1 and retries): a reserved file ID.** Reserve the folder ID with `files.generateIds` and store it before creating, then create with that ID. A retry reuses it: Drive refuses a second file with the same ID, so the retry never makes a second folder. This is the same pattern TL-P2-05 uses for uploads.
- **Template completeness.** The pointer records whether the template is complete. Each call before completion adds the missing template items by name, create-only, so a fill interrupted by a Drive failure finishes on the next call. Nothing existing is ever overwritten or deleted.

**Accepted deviation (2026-10-07).** The Drive calls cannot run inside the person object, because the tests inject `fetch` per request. The object therefore grants a 60-second creation claim instead, which is an expiring lease. To make the whole fill idempotent however long it stalls, the template files' IDs are reserved in the same `generateIds` call and stored with the folder ID. The claim is not renewed. One Opus delta review covers the claim and the reserved template IDs.
