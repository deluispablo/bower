  - **Dispositions.** Every item in the admitted manifest ends with exactly one recorded disposition (`pile-disposition.ts`):
    - filed;
    - set aside: it stays in the inbox, untouched;
    - waiting: it changed since admission.
    No item is left without a disposition, and none has two.
  - **The report barrier.**
    - After the last operation checkpoint, the runner writes the report files: `.bower/questions.json`, `suggestions.json`, `requests.json` and `hashes.json` (shapes in `layout.ts`), then `.bower/last-run.json` last (`{ v: 1, run: <RunWire with report> }`).
    - It reads `last-run.json` back and compares `md5Checksum` with what it wrote.
    - Only then does it report `done`.
    - Before any write, the runner checks the folder for this `run_id`'s report (contract, "Runner wire").
  - **A failed report save.**
    - The run stays in `saving`, and the chain records "effects done, report pending".
    - A redispatch reads that checkpoint, applies no effect, and writes only the report.
  - **Past the ceiling.**
    - In `api/src/recovery.ts`, a run that is still in `saving` when it reaches the recovery ceiling ends `failed`.
    - Its failure is the sentence `Bower made changes but couldn't save the summary of this tidy-up.` (a constant beside `STALE_FAILURE`), never "stopped before changing anything" or "took too long".
    - Other phases keep `STALE_FAILURE`.
  - **The runner is wired.** `runner/src/main.ts` calls token → spine → barrier → status (`POST /runner/runs/:id/status` with `{attempt, seq, phase}`), so the runner runs end to end. Its test injects a provider stub and fakes the Worker and Drive over fetch; it never reaches the network.
