# Technical-lead decision TL-P2-2026-10-06-35: a merge Bower cannot add files the thing on its own

Lead: Claude `Planificador`. This answers the blocking finding in `b-path-merges`, and it replaces the merge part of the TL-P2-34 amendment.

**Ruling: option (3).** It is the simplest proven option: one run, no stuck state, and an honest report. Sometimes a merge line is refused at plan time, because the target note is too big, has an unsupported format or is not valid UTF-8. Then:

- **The thing is filed on its own,** as an ordinary item, which is the same fallback as I7.
- **The report keeps its `filed` row** and adds a `setAside` row with "Bower couldn't add it to <note title>, so it was filed on its own." The row is an applied contribution on the move, the same pattern as "Bower couldn't write its note." in TL-P2-32. `<note title>` is the note's shown name, not its file name.
- **The answer is archived and the question removed.** Under R4-1, the operations derived from the answer are now the ordinary filing, and their dependencies still apply. A rejected move keeps both, as before.

Holding the pile is withdrawn for this case. It left a pile that looked ready, with no reason anywhere, which breaches TL-P2-21.

**Minor: follow `into` through the run's renames, as the resolver does.** A target renamed in the same run still receives its merge. Approved.

**`pile-note-read-isolation`: register and assign it.** This was already answered: it applies TL-P2-08 (a) to pile notes, with no repeated errors when the whole app is offline.
