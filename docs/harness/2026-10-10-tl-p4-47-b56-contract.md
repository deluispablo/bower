# Technical-lead decision TL-P4-47: the B5 and B6 contract (type table, profiles, templates, fit → create → ask)

These are the rulings on the 7 questions in Codex's refreshed B5+B6 preparation draft (p4-b56-prep bdb471ca, `2026-10-10-b56-prep.md`). The draft is accepted as the base, with its entries B5a, B5b, B5c, B6a, B6b and B6c, and its file ledger. It follows TL-P4-38, TL-P4-39 and its addenda, TL-P4-41 to TL-P4-46, and the owner's principle of designing for normal use.

**What needs the owner's OK.** Everything here is note content or hidden files, except one item: the folder Table showing the type row's declared columns instead of the first four property keys (Q1). That changes what the person sees, so the designer specs it and the owner OKs it before B5b's Table part is built (TL-P4-40 (3)).

## Rulings

- **Q1. The type table.**
  - It is stored as `.bower/type-table.json`, versioned, rather than Markdown. It is hidden and runner-owned, so it uses the existing `write-runner-json` effect and its validators, with no new effect kind. The runner renders it as a Markdown table in the prompt (position 2).
  - Rows have stable slug ids, and the first match wins. The seed has 8 rows: the 7 in TL-P4-38's appendix plus the cover letter. Accepted rows are inserted before the generic fallbacks ("other project material" and "other area material").
  - Values are bounded: text up to 200 characters, a list up to 10 items, an enum up to 20 values, finite numbers, money as an amount plus an ISO 4217 currency, and ISO dates.
  - Writes are strict and reads are lenient. An invalid row is skipped (B8's health note reports it later). An unreadable file means the seed rows are used, and the table is not written that run.
  - The Table projection shows the row's declared `table` subset, at most 4 columns. The technical keys (type, status, summary, tags, created, updated, source, related) are never columns. The other properties stay in the note. This part waits for the designer and the owner's OK.
- **Q2. B1e's split criterion.** A type row may declare `group_by`, naming an enum property, or a date property grouped by year. A folder with no row criterion groups by the year of `created`. A note without a value goes in an explicit "Other" group. Names and order are deterministic, and the model invents no taxonomy. B1e keeps its rules: 40 direct members, singletons unchanged, and a depth of 3.
- **Q3. Proposals.** As recommended:
  - at most 2 new distinct payloads per run, in admitted-item order, deduplicated by payload;
  - at most 5 open proposals at once, so Home is not flooded; further proposals wait;
  - an ignored proposal stays open, and a declined payload is never proposed again;
  - a yes starts the existing answer loop once and installs exactly the frozen payload, and a no starts no run.

  Proposals are not inbox subjects, so Q1's 2-round cap does not apply to them.
- **Q4. Profiles.**
  - A profile is a Bower note with a new Bower region of at most 400 grounded words, written through note-edit. The short Current state stays separate, under C05's bounds.
  - The first document that matches a row with a profile creates the profile from the row's template; for example, the first CV creates the career profile.
  - A note the person wrote is never adopted, and a profile is never picked by an ambiguous title. When the target is unresolved, the filing proceeds and the profile is not updated. There is no new report row; B8's health note covers it later.
- **Q5. Templates.** As recommended. Goal and Next steps are Bower regions in note-edit. A new Source or MOC gets no generated Timeline, and legacy Timelines are kept unrewritten. An absent url is omitted, never invented. The hub counts among the 1–5 related links, and there is no padding with unrelated notes.
- **Q6. Create or reuse.** As recommended. A new Project needs an explicit grounded goal or end in the admitted words or source, carried as a typed basis in B1's selection. Otherwise the material goes to an existing Area or Resources. Near-name matching is a script normalization (case, Unicode NFC, punctuation, a leading article), and the model judges fit only among visible ids. An ambiguous choice or a cut index goes to Q1, never to a guess.
- **Q7. TL-P4-41 addendum 4** (B1a's measured calls): B5 and B6 add no `maintain` writes. Writes to the type table and proposals are planning effects of the run. Profile, template and MOC writes are ordinary note effects, and their reads reuse the run's read cache. Maintain stays bounded to retrieval.json, index.md and changed MOC regions.
