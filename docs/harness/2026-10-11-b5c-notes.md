### Scope blocker and required existing homes

The packet's Owned files and Ruled section allocate scripted.ts, claude.ts, note-edit.ts, TypeRow,
note-format.ts and NOTE_TEMPLATES, plus the specimens. They do **not** allocate the following production
homes needed to satisfy the ordinary-effects contract. This is an allocation gap, not another claim that
B5b must implement B5c, and addendum 12's per-item reply contract is sufficiently specific.

1. **src/data/spine/engine.ts and src/data/contracts/run-manifest.ts: first-created target identity.**
   The engine reserves every create's real Drive id in opening(), after manifest persistence, and keeps
   that identity in checkpoint outcomes. A type-table write currently has only frozen text and content;
   it cannot bind a row's profile id to a dependent create outcome. The existing afterMove() binds
   dependent edit/create targets but does not bind JSON field values. First creation needs an extension
   of this same ordinary write/checkpoint resolution, with validation, dependency on the profile create,
   content hashing and recovery. Binding a createKey, operation id, title or path as a Drive id is wrong.
   Creating first and discovering by title on a later run would violate the stable-id and replay contract.
2. **src/data/spine/grounded.ts: profile update rows.**
   grounded() admits an updated row for a state/about edit or a Timeline entry, but not a profile-only
   edit. An exploratory real id-bound profile edit with its ordinary applied updated row was refused:
   `the plan has report rows its effects do not ground`. This one report guard needs to recognize a
   profile region edit. Adding an unrelated state or Timeline effect solely to pass that guard is not
   a valid substitute. No alternate profile writer or report path was retained.
3. **Selection budget red needs a ruling on read accounting.**
   `runner/test/b5c-profile.test.ts:223` asserts one full media read across the entire main run, not only
   shared context selection. Today's provider reads selected text, the planner's verified edit reads
   bytes, and the engine reads bytes again for recheckEdit at application. ReadCache.text can reuse
   bytes, but ReadCache.bytes does not reuse text; RunnerDrive's effect reads intentionally bypass the
   planning cache. Context reads can be deduplicated in the existing reader, but the fresh application
   fence must not be removed just to meet this count. Decide whether this red counts planning reads
   only, or allocate the existing reader/engine homes for a version-safe optimization. No contract
   number or test was changed.
