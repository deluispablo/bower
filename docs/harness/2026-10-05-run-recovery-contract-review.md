### Important: the structural DriveId pattern rejects valid fixture identities

Location: `/private/tmp/bower-p2-run-recovery-contract/contract.md:250`, `$defs.DriveId.pattern`; corresponding archived contract at `docs/harness/evidence/2026-10-05-local-prerequisites/run-recovery-contract/contract.md:250`. The literal JSON schema stores `"pattern":"^[^\\\\u0000-\\\\u001f\\\\u007f]+$"`. After JSON decoding, the regular expression still contains two backslashes before each `u`. Those pairs express literal backslashes in the character class, followed by ordinary `u`, digit/range and `f` characters; they do not express Unicode control escapes. In particular literal `f` is excluded, so ordinary expected identities such as `fake-root`, `receipt-file` and `inbox-folder` fail this structural pattern, despite being accepted by the normative opaque-ID prose and used throughout the positive fixtures. Controls are also not excluded by the intended Unicode range in this literal schema. Normative runtime guards independently require rejecting controls, so this finding does not claim implemented unauthorized I/O.

A producer/hand-written guard following the TypeScript/prose and a consumer following the literal schema disagree on the same valid record. Suggested correction: encode one regular-expression backslash per Unicode escape after JSON decoding, i.e. the JSON source should use `"pattern":"^[^\\u0000-\\u001f\\u007f]+$"`.
