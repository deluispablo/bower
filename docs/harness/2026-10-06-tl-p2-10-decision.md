# Technical-lead decision TL-P2-2026-10-06-10

Lead: Claude `Planificador`. This answers the five questions in the coordinator's O4 unit packet (`docs/harness/2026-10-06-o4-unit-packet.md` on the integration branch). Adopted revision stays `2026-10-05-contracts-2`, contract B is unchanged, and TL-P2-06 stands.

The split is accepted:

- **U1** is `run-report-save-barrier-legacy`. It touches only `fake-worker.ts` and can run in parallel with readiness.
- **U2** is the B path. It comes after readiness, and the parent `run-report-save-barrier` closes with it.

No seeded scenario qualifies for the B path today. That confirms the coordinator's record: P2 cannot close while any plan reaches the legacy path.

## 1. Clearing a "new" mark is a B `move` in place: yes

The `move` effect already carries `properties`, and `bowerNew` is one of them. Clearing the mark is a `move` to the same parent and name, with `properties` exactly `{ bowerNew: null }`. Four conditions apply:

- The file must still be at the captured place with the captured name (`stillAsSeen`). A text edit since then is no conflict.
- It applies only to marks that Bower set.
- It adds no row to the report: no `filed` or `updated` entry, and it counts toward nothing.
- Its evidence shows the same parent and name and the mark cleared.

Without this, the B path could run only once per folder.

## 2. The barrier also holds back `failed` on the B path, not on the legacy path

- **B path.** Public terminal phases are derived the same way for `done` and `failed`. The service first commits the terminal checkpoint (the honest-phase rule already forbids `failed` once an effect has applied). Then it writes and reads back the v1 view. Until the view matches, clients see the last confirmed non-terminal phase. A new `process()` call returns the same run and lets the service publish it, so the person is never blocked.
- **Legacy path.** A `failed` ending is shown at once, with its honest failure text, and its view save is retried in the same way as `done`'s. A failure claims no success. Holding it back would leave the page in `saving` and block the person's retry. A reload already turns a cut-off legacy run into the honest `failed`.

## 3. Journal and generated notes stay on the legacy path in this cut: accepted, if registered

Contract B already defines grounding for `requests` and `yourChanges`. Generated notes, though, still need a destination and ownership rule that B leaves to a later proposal. Keeping both on the legacy path for U2 is fine. Register two entries before P2-H:

- **`b-path-journal`**: journal archive, requests and `yourChanges` on B's existing grounding.
- **`b-path-generated-note`**: needs the generated-destination rule. The lead will give it as its own TL decision when this entry is next.

## 4. Created folders: not by name alone

A folder that appears with the same name and parent after the capture would be wrongly taken as Bower's. B says a lookalike never proves an operation applied. Instead, use one of these:

1. **Preferred:** a reserved file ID (pre-generated, TL-P2-05). This applies once the fake Drive supports reserved IDs, which `upload-queue-persistent` phase 1 adds. Reconcile by reading that ID.
2. **Until then:** stamp the existing idempotency property `bowerItem` with the operation's `createKey` on the created folder or text. Reconcile by key, name and parent. A same-named folder without the key is an unrelated lookalike: the outcome stays unresolved and is never marked applied.

No new property name is needed. The P3 adapter must offer the same provenance.

## 5. Declared piles may stay legacy if U2 grows: yes, as a registered sub-unit

If U2 grows, classify declared piles as legacy and register **`b-path-pile-disposition`**: consumed dispositions under guard 13, as in the O4 packet's last scenario. It closes before P2-H, and before any O5 entry relies on dispositions. Parent closure then states that declared piles are not yet on the B path.
