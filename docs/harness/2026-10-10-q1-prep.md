## Drive calls, tokens and elapsed time of a continuation

Estimates/formulas, **not measurements or newly approved limits**. A continuation is a new normal run: it pays admission, GitHub queue/start, token/attempt fencing, context, manifest/checkpoints/effects, maintenance and report again, and counts against quota (TL-P4-39 F6). It does not hold the first runner open waiting for the person's time.

Let L be admission listing pages; J relevant admitted journal files; K waiting members plus required pile anchors/context; C control/declaration/context media reads; U unique context notes (within five/source and shared text limits); R source media/extraction reads for waiting items; E actual effects and verification traffic; H manifest/checkpoint/barrier/retention traffic; M B1/B3 maintenance traffic. Account OAuth refresh, Drive retries, ancestry/changes pages, and journal create/reconciliation separately. Test seed/snapshot reads are excluded from production budgets.

| Path | Drive/API effect | Model tokens/time effect |
| --- | --- | --- |
| Answer saved, then idle admission | Existing journal reserve/create/reconcile path; `flushJournal` first (`live/runs.ts:116`). New run: roughly **L + J + C** admission reads under existing Worker subrequest budget; runner rechecks **K + J** admitted metadata plus **C + U + R + E + H + M** traffic. Not a universal fixed call count; bounded listing may still span all folder metadata. | Existing placement/free-text model call(s) rerun only for waiting items and answer, with ordinary context overhead; queue/start and report cost recur. Stored-state shown update can still use **zero model calls** (`claude.ts:1174`). |
| Answer during active run | Answer journal cost now; Person queues it with **zero admission Drive reads** at `/process` (`process.ts:24`, `person.ts:688`). After end, one grouped continuation pays the same admission/runner cost above. Status publication/polling adds Worker requests, **zero Drive calls** on GET /status. | No concurrent model/runner; elapsed includes remainder of active run + queue/start + continuation. Two waiting answers batched share fixed context/start costs, not two jobs. |
| Duplicate answer/run request | Existing one-line coalescing/write-once and admission requestId lookup; known request or active wait has no admission Drive scan. Lost response may incur safe readback/retry calls; never call that zero total cost. | No new semantic plan for a completed replay; status retransmission has zero model tokens. Same-run recovery uses persisted plan instead of re-planning (`main.ts:238`). |
| Round 2 then exhausted | A second actionable answer may require a second continuation; failed placement leaves item untouched and durable exhaustion. No third automatic question/answer job. Maintenance may still update derived thread state through its existing effect. | Up to two answer continuations after the initial asking run for an unresolved subject under proposed Q3 interpretation; this is a bound on question rounds, **not on all run attempts or every future deliberate request**. Q8 must settle aggregate request accounting. |

Illustrative incremental scope: one waiting file, one pile anchor and one relevant answer imply **3 admitted metadata rechecks**, plus media/context/control/effect/checkpoint/report/maintenance calls. Current containing-pile/all-journal admission can make those much larger, which is why Q4's red must assert ids and actual media trace. Exact savings depend on listing breadth, cached prefix/full reads, source type and warm retrieval state; do not promise “only one Drive read”. The initial live question must not incur a full Drive refresh on every poll.

Token formula per planning call: input ≈ `(fixed instructions + allowed index/Rules/About me/hot/neighbourhood + waiting source text + question/answer text) / 4` as a rough English character heuristic; output is the validated intent/wording. Store actual model usage including cache-read/cache-creation tokens and retries (`claude.ts:1130`). Script-built options/status/round counters cost **0 model tokens**; question wording belongs in the existing call, not a separate wrapping call. A text answer adds its bounded characters; excluded unrelated sources/journal instructions must not enter model input.

Before B1d, the existing provider uses one execution call with one validation retry (`claude.ts:1259`); after B1d, expect selection + execution under its shared ledger. As a sizing illustration, 8,000 chars fixed/context + 4,000 waiting source + 400 question/answer ≈ **3,100 input tokens**, plus output, per call. This is not a fixture measurement or a cap. Repeating such a continuation twice costs roughly twice its per-run planning overhead; B1's allowed index alone can be 32,000 chars (~8k tokens), so wider context can dominate. No prefix-cache dollar saving is assumed.

Elapsed-time formula for an answer now: `journal flush + admission + dispatch/queue/start + runner reads/planning/effects + maintenance/report/retries`. While waiting add the remaining active-run time; exclude human response time from runner runtime. Keep existing **200 items/30 minutes per request**, **20% reserve**, **300 maintenance Drive calls/run**, 24k note/48k source chars and five notes/source; these do not authorize a fresh budget for every retry. TL-P4-39 addendum 3's later “now the rest” is a new B12 request with 30-day cached results skipped, distinct from Q1's answer continuation of waiting items. Measure cold/warm continuation actual admission reads/bytes, model usage, queue/start, per-phase time and retries before acceptance; no elapsed claim is made in this prep.
