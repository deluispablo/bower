## Unreadable runner files (`b-path-unreadable-runner-files`)

These are `.bower/questions.json`, `.bower/requests.json` and `.bower/hashes.json`.

- **The read fails** (Drive error or offline). The run refuses before any effect and before admission with "Bower couldn't read its own files. Try again." It records no manifest and leaves nothing half done.
- **The file reads but is malformed.** It is Bower's own derived file, so the B path replaces it with a fresh, valid file through `write-runner-json`.
  - The `beforeContent` hash of the bytes it could not parse is recorded.
  - Drive keeps the earlier revision, so nothing is destroyed.
  - The report never claims the old entries.
  - A `BowerError` goes to the console.

  A malformed file never blocks every future run.

## The generated-note destination rule (`b-path-generated-note`)

This covers what B left to a later proposal for `create-text` with `purpose: 'generated'`: generated notes and a filed item's companion note (`plan.note`). Revising a generated document later (C08) needs its own ownership decision.

- **Place.** Inside the person's Bower folder, under one of the main folders or a folder the same plan creates there. Never in Inbox, never under `.bower/`, never at the root.
- **Name.** Built from the authored title with the app's existing naming rules, as `.md`. The name is made unique at plan time against the captured places with the existing `freeName`. At apply time, an existing file at that path counts as this operation only when it carries `bowerItem` = the operation's `createKey` (TL-P2-10). Any other lookalike is a conflict: the operation is rejected, and the item goes to `setAside`.
- **Marks.** `by: bower` and `bowerNew: 1` are stamped at creation, plus `bowerItem` = `createKey`.
- **Report.** `created.path` equals the resolved path, and `what` is the authored wording. A companion note appears in `filed.note` only when its create applied in the same `requires` set (B's grounding rule).
