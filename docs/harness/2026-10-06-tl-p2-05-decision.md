## R1 remains an acceptance blocker

Our actual GET then PATCH experiment lost a confirmed competing edit. The later ETag experiments were inconclusive; this is not a general impossibility claim about Drive. No demonstrated solution currently preserves all four requirements together: Markdown at the same file ID, immediate save to that file, external noncooperating writers and no lost changes. Another read, rebase, postcheck or Worker lock does not establish an atomic provider condition or close the observed race. Do not build a synchronization layer or a fake scenario that disguises this gap. The ETag line remains ended.

The lead recommends **Save a copy** for a future owner decision if that line stays closed: preserve the source, create a complete edited Markdown document under a new stable operation/file identity, verify it before reporting copy success, open it and link its source. Explicit reconciliation keeps both versions. Never automatically overwrite, replace, Bin or rename the original to simulate a safe replacement. This changes identity, links and the editing flow; it is not adopted, does not resolve C03 and has no implementation/activation assignment during the owner's absence. Do not spend another unit on this alternative now.

Such evidence would prove the copy operation, not safe same-file merging. R1-OBS01 remains open and prevents P2 acceptance/P3 entry; continue independent work.

## R2 identity boundary

The lead specifies a validated OpenID Connect subject for real principal identity, with signature, issuer, audience, expiry and nonce/context validation appropriate to the flow. Email, display name and access to a shared root are not substitutes. A-only access does not demonstrate real two-principal isolation. Do not revoke production authentication for testing; negative token/epoch/stale-reply fixtures and a separately authorized second account are distinct evidence. See [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect). No real second-account result is claimed.

## R4 reservation recommendation

The lead recommends official pre-generated file IDs rather than heuristic duplicate discovery. Google documents upload retry with an assigned ID and a conflict response for an already successful create; ordinary files and folders are supported, native Workspace conversion has documented exclusions. Root independently read the relevant official sections on 2026-10-06: [uploading with pre-generated IDs](https://developers.google.com/workspace/drive/api/guides/manage-uploads#pre-generated-ids) and [files.generateIds](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/generateIds).

The proposed mechanism persists a private trusted logical-operation-to-reserved-ID binding before creation, with authorized parent and intended byte/hash data. A reservation is not an existing file. On a timeout, read that same ID and verify the complete result; a conflict response alone never means success. Keep the same reservation across retries. Resumable URI/confirmed offset remain private; missing local bytes require hash-verified reselection. This is a recommendation and documentation finding, not provider proof, a change to ratified B or activation of a real upload protocol. Prepare one bounded R4 case with explicit budgets, cleanup and independent review when ready; do not reopen R1.
