# Technical-lead decision TL-P2-2026-10-06-29: the simplest-approach rule applied to four open entries

Lead: Claude `Planificador`. This applies the owner's simplest-proven-approach rule (TL-P2-28) to the coordinator's four candidates.

1. **`note-edit-consumer-limits`: at most 8 `edit-text` operations per run, taken in path order.** The rest wait for the next run.
   - **Why the count is enough.** Each edit is at most 1 MiB, so the count bounds the manifest at 8 MiB. That replaces the 8 MiB deterministic deferral (R3-7 m7).
   - **Why it converges.** Records whose edits wait stay unarchived (rule 7), so the resolver keeps following former names. Skip-if-present makes the next run converge.
   - **The "needs a newer Bower" message** stays as ratified, and adds no new mechanism.
2. **`declared-pile-folder-lost`: accepted.** A declared pile whose folder has gone, other than through the person's Bin, shows as set aside. It uses the existing reason "Nothing is left in it. Remove it from your inbox." and its Remove action. Remove retires the declaration through the person's removal. There is no separate "lost" mechanism.
3. **`fake-drive-reservation-saved`: accepted.** Save the pretend snapshot immediately on `generateIds` and on each chunk.
4. **`b-path-leftover-piles`: interim only.** A leftover pile may take the legacy path while that path exists. It cannot be a permanent limit, because `o5-no-legacy-run-path` must still prove no plan reaches legacy before P2-H. The coordinator names the concrete blocker that keeps a leftover pile off the B path, and the lead then picks the simplest rule. The default expectation: it is an ordinary pile for the next run (TL-P2-21).

**Amendment for item 4 (same day).** The blocker: after a B run files a declared pile's members and keeps the folder (a late child or a loose note), the next run sees a declared pile with no declared member present, and falls back to legacy.

The rule, confirmed: a declared pile whose declared member keys are all accounted for is treated, for what remains in its folder, as an ordinary observed pile.

- **Accounted for** means covered by consumed dispositions, which the earlier B run wrote for the members it filed (TL-P2-09), or arrived-and-left by the lookup (TL-P2-09 and TL-P2-12) for members filed by legacy.
- **The capture.** The leftover is captured with null member keys. Its context is the bound note if there is one, otherwise the first note (TL-P2-21). B files it normally.
- **The declaration.** Keys already disposed need no new disposition. The declaration file stays as history.

No external standard applies; this is internal to contract B.

**Second amendment (same day).**

- **A declared pile that is partly filed: confirmed.** Members already accounted for count as filed, whether by a consumed disposition or by the lookup. Members still inside are captured as declared members of the same pile. Their readiness is judged on the remaining keys only, and B files them. No new mechanism.
- **The Inbox and the runner use the same rule.** A separate small entry makes the Inbox's readiness read the consumed dispositions too. Today `DriveVault` uses the lookup only, so a member edited after a B run filed it shows as "changed" in the Inbox while the run treats it as filed.
  - **One shared function.** The accounting rule (dispositions, then the lookup) moves into the shared readiness module (`pile-readiness.ts`). Both the runner and `DriveVault` call that one function, so the two can never disagree again.
  - **Test.** It covers a member edited after filing: the Inbox shows the same readiness as the run.

No external standard applies; both points are internal to contract B.
