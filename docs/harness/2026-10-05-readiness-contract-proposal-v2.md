## Preferred bounded contract

**Declaration and publication.** Before uploading members, mint one logical pile identity and one immutable member key per exact selected file/link/context requirement. Persist a supported-version declaration scoped to the authoritative signed-in account/Bower-root context; record creation time, exact original instruction text, expected item order/names/kinds/origins, keys, sizes and content hashes (canonical .url bytes for links; context included). Provider IDs cannot be invented before creation. The first-create authority depends on the preserved layout. For a loose single file/link without context, a confirmed/reconciled immutable declaration, independently verified authenticated Bower-root and actual Inbox parent, and a stable member/create-intent key authorize its initial create in that Inbox. Its own file ID is not a precondition: bind the returned actual ID only after a unique in-scope effect is reconciled to that declaration/key, expected parent and content evidence. For a real pile folder, reconcile the actual folder ID, parent and declaration binding before creating any child or context file. Creation-time appProperties carry the agreed logical key and opt-in declaration reference; missing/corrupt referenced declarations never become external input. Keep the declaration and member/create intent stable through refusal or an unknown response, with original scope/body identity; no duplicate intent for changed bytes and no blind repeat after a possible effect. Failure/unknown declaration or parent/folder authority before the applicable initial create preserves the Add draft and refuses member dispatch. A before-effect member refusal permits the same logical-key retry once the original authority/bytes are revalidated; a possible-effect create requires reconciliation first, otherwise remains unresolved. Exact trusted authority, intent persistence/binding, completion evidence and producer/consumer activation remain for lead adoption. No empty placeholder file, mandatory new pile folder, binary-update API or new layout is proposed.

Use immutable per-pile records, not a shared read-modify-write counter or mutable ready flag. Resolve identical duplicate declaration copies once by stable logical identity + canonical bytes/hash; differing copies are a conflict. Enumerate hidden bookkeeping by actual parent IDs/names, including duplicate `.bower`/namespace folders, as VaultIndex already does for journal files. Never use a disambiguated visible path as durable identity. Preserve the existing loose-single-file/no-context layout and all legacy note-only/multi-file layouts; a pending lone member is discoverable through its declaration even before its file exists. That requirement is why a declaration only inside a pile folder is insufficient.

**Reconciliation and recovery.** A member is complete only when its actual in-scope effect is reconciled to that exact key/anchor. Original names are display metadata, not dedupe identity. Several matching files, an unexpected parent/account, a changed payload or unknown/unverifiable completion blocks consumption and automatic retry. Metadata progress or `upload:1` does not prove stored bytes. Normal successful upload confirmation and fresh unique-key lookup can supply the current adapter's evidence; metadata carrying an expected hash is not an independent cryptographic proof of remote bytes. In the actual lost-response case, content/size evidence must be verified through the separately accepted R4/read/extraction capability; if unavailable, preserve an unresolved row instead of guessing from a name. The current DriveApi has no general binary-read/content-hash method; this proposal does not fabricate one.

A fresh client lists every declared member and original context, joining completed siblings with placeholders for missing/unresolved members. Existing `PileItem.upload` values may render missing rows and current Try again, but durable readiness must not be stored only in that UI number. Original live uploader retries only the failed key with retained bytes; completed sibling keys are not sent again. A fresh client with no bytes must return a readable reselection requirement rather than today's no-op. D02 retained bytes are best-effort, scoped by account/root/pile/member; reselection must match declared size/hash/identity before using the **same** member key. S02 already clears retrievable pending-draft references in the current-page holder when central person cleanup is invoked, even when subsequent Storage access/removal is blocked. Storage denial alone does not invoke that cleanup or discard current-page bytes; Add deliberately keeps its in-page draft. S02 supplies no durable Blob store, quota/eviction listener or unconditional retention guarantee. Future D02 best-effort retention and unavailable-byte detection/reselection, and the proposed remote missing-member discovery, remain unimplemented obligations: unavailable bytes must be visible and content-verified reselection must preserve declared membership/completed siblings. Wrong file/account selection causes no upload. No pending record or original-folder outbox is forwarded to another account.

Context's original bytes in the declaration are a recovery copy, not authority to overwrite a newer Pile note. Before capture, read the actual current context and capture its version/hash; supported user context edits remain allowed. Missing required context blocks readiness. Do not restore stale original words automatically. Existing updatePile mutable text writes and any proposed declaration rewrite would depend on R1; the preferred declaration never gets rewritten.

**Capture and consumption.** Select only fully reconciled inputs; preserve all blocked piles and explain them via existing safe error/report conventions. If no ready input exists, refuse before filing/Bin; unrelated instructions follow their own scope. If another ready pile runs, blocked piles remain pending and are named in existing setAside rather than silently omitted. Capture exact file IDs/member keys, content/version evidence, container/name/place and context; do not reconstruct membership from a later listing. Revalidate captured inputs before effects, and never add later arrivals to this capture. A member that finishes after capture, a new pile, or an added child waits for a later run.

The runner must never Bin a parent containing an uncaptured child. If arrival is detected before effects, refuse/rebuild a new capture; if detected after some effects, retain parent/context/remaining originals and expose the partial state under the separately adopted O4 effect/report contract. Do not infer completed run identity from a missing parent. A declaration cannot itself prove filing/report completion: lifecycle retirement/removal must be tied to an explicit scoped completed/removal disposition agreed with O4, avoiding ghost pending records or rerunning filed members. Keep records/originals until that disposition is demonstrable; do not invent a checkpoint enum, terminal wire extension or scheduler in this entry. Deliberate pile removal is Bin-only, includes its declaration/recovery disposition, and must remain compatible with Undo.

**Real dependencies.** Immutable declarations avoid a new mutable-content CAS dependency; concurrent create/unknown-response reconciliation still needs R4 evidence. Current context edits, semantic writes and parent move/rename/Bin safety do not become atomic through this inventory: R1-OBS01 and remaining name/place races remain open. Persisted capture/same-run recovery/retirement require O4 authority and compatible report mapping. Browser-independent admission is not proved by a new memory snapshot. Prefer proposing this contract now; activate only the accepted slices, without claiming these later dependencies passed.

Exact rollout capability and compatibility window are **lead decisions**, not a new wire field adopted here. Unmarked old partial piles cannot be retroactively recovered after their browser lost expected members; retain them and require explicit user selection/reconciliation rather than certifying completeness. Persisted current runner JSONv1, valid done/failed/reportless controls, JournalRecordv1 and note grammar remain unchanged. Extra readiness fields must not silently tighten those validators. If an old backend cannot refuse a new producer, activation is blocked; UI-only capability hiding cannot secure a fresh old runner.

At most one alternative: a mutable per-pile ready manifest updated as members arrive. It is smaller superficially but adds concurrent writers/lost acknowledgements/stale completion flags and therefore depends on a demonstrated R1 conditional-write remedy plus operation reconciliation. **Do not choose it now.** The immutable declaration + derived observations is preferred; no third design or new library is needed for this scope. Retain current guards/primitives; later idb storage adoption belongs to D02/O6 with a pinned release/license, not this metadata repair.
