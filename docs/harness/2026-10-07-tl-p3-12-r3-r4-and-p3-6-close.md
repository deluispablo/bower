# Technical-lead decision TL-P3-2026-10-07-12: what R3 and R4 run against, and the P3-6 close

**Coordinator questions, 2026-10-07:**
- Does P3-6 get a review?
- What do the load flakes mean?
- What do R3 (`r3-executor-probe`) and R4 (`r4-resumable-reserved-id-real`) run against?

The probe specs date from P2 ([R-probe specs](2026-10-05-p2-r-probe-specs.md), [R4 spec review](2026-10-06-r4-reserved-id-spec-review.md)). They were written for a time when there was no Worker, no real sign-in and no person object. So they built their own control doubles and listed missing preflights. P3 now has all three, which lets both probes shrink to what only the provider can answer. Everything that is Bower's own logic is tested in its own entry against the fakes, as P2 did (owner rule: simplest proven approach).

## P3-6 close

- **One Opus delta review at the batch close** ([TL-P2-46](2026-10-06-tl-p2-46-review-fallback.md) fallback). It covers the `runs.ts` retry, `settle()` and the `/status` route, against their acceptance contracts. `settle()` decides what a person is told after an ambiguous write, which is data-safety work, so it warrants the review.
- **Load flakes.** `fake-worker.test.ts`, `run-manifest.test.ts` and e2e `qa5:38` on phone run only at the batch close, on an idle machine with no worker running. If any of them fails there, it becomes an entry. A wait is not raised to make it pass: the entry finds the slow step first. A pass on an idle machine is a polish note.

## R3: provider premises only, on a staging instance repository

**It does not wait for `worker-process-admission`.** Admission, expiring claims, ticket authentication, status revisions and stale-attempt fencing are Bower's own code. Each is tested in its own P3-C entry with fakes, and their live delivery is covered by the C12 staging journeys. The P2 control double is dropped: the person object is that double, for real. R3 measures only what GitHub decides.

**Where it runs:** a new private staging instance repository, never the original production instance repository. That repository's workflows report to the production Worker, and production stays untouched in P3 ([TL-P3-08](2026-10-07-tl-p3-08-production-guard.md)). The original's `scripts/new-instance.sh` is the reused way to create it. P3's runner later uses the same repository, with the owner's Claude credential set by the owner.

**Owner setup, pending authorization:**
1. Create the repository.
2. Authorize pushing the probe workflow there. This is an exception to "development stays local", like the backup.
3. Pushing a file under `.github/workflows/` needs `gh`'s `workflow` scope, so the owner runs `gh auth refresh -h github.com -s workflow`.

R3 starts when the owner has decided.

**The probe workflow:** no model, no Drive, no secrets, a 2-minute timeout. It accepts only synthetic run and request ids, sets `run-name` to the request id, and uploads a small report artifact. Its `concurrency` group is the one P3 intends for a run: per run id, with no `cancel-in-progress`.

**Method.** Bounds: eight dispatches in total, 30 minutes in total, dispatched with `gh api` against that one repository only.
1. **Three serial baselines.** Record the times dispatch → run created → started → completed. A 204 with no run is "accepted, not observed", never a pass.
2. **Two same-run duplicate dispatches.** Record whether both start, one queues or one is cancelled, under the actual concurrency setting.
3. **A lost dispatch reply.** Treat the 204 as unknown. Find the run by its `run-name` before any redispatch, and record that exactly one logical run exists.
4. **A lost completion.** There is no callback. The observer reconciles from the run's conclusion and its artifact, which is the original's job-conclusion fallback. A run with no artifact is never called done.

The result gives individual timings and their range, with no percentiles. It feeds the stale-run thresholds in `worker-stale-run-recovery`. A stop on a missing permission, an unexpected action or a passed bound is reported, never retried.

## R4: the coordinator's evaluator packet, confirmed

R4 is a page script in the pane, run as account A. Everything it creates goes inside the probe folder, and the packet gives that folder's id. The token comes from the Worker's Drive token route. That closes the preflight the R4 spec review found missing: a validated subject is now R2's real sign-in.

- **Part A, reserved-ID create with a lost reply.** Follow the frozen spec's itinerary and bounds: 24 HTTP attempts, 196608 bytes, 360 s. Logging is per attempt in the page script, and there is no separate instrument. Expected result: the same-ID retry gives 409 and exactly one file ([pre-generated IDs](https://developers.google.com/workspace/drive/api/guides/manage-uploads#pre-generated-ids)).
- **Part B, a resumable upload interrupted by a reload.** This follows the P2 R4 method, without the inventory and byte-retention steps.
  - Upload a deterministic 10 MiB binary (bytes `offset % 251`) with one 8 MiB chunk, then reload the page.
  - A fresh page sends the status query (`Content-Range: bytes */TOTAL`) and resumes from the offset the server reports.
  - Check: one file, the right size and a matching `md5Checksum`.
  - Separately, withhold the final reply, then reconcile with a status query before any new create.
  - The session URI is never logged.
  - Bounds: 80 requests, 40 MiB, 15 minutes.
- **Cleanup:** move only what the script created to the Bin, with no hard delete. Nothing is read or listed outside the probe folder.
- **Moved elsewhere:** the P2 R4 steps on pile inventory and readiness, retained bytes or reselect, and the account switch with an upload pending are Bower's own logic. They go to `upload-queue-real` and `declare-piles-real` as tests against the fakes. Retained bytes versus reselect stays an owner policy question for `upload-queue-real`.

## Amendment, owner answer: R3 uses the existing instance repository

The owner chose the existing private instance repository over a new one ("para eso está"). That is consistent with owner decision 2 of P3_DRAFT. Production stays untouched because R3 adds one file and changes nothing else:
- **The only change is `.github/workflows/probe.yml`,** listening to `repository_dispatch` type `bower-probe`. The production workflows listen only to `ingest` and `bower-lint` (checked 2026-10-07), so a probe dispatch never starts them.
- **Left as they are:** the production workflows, the repository's variables and its secrets.
- **The probe workflow copies the production concurrency pattern:** a group per id, with no `cancel-in-progress`.
- **The lead pushes the file and deletes it after R3,** each as one commit on the default branch, after the owner grants `gh` the `workflow` scope. These are the only pushes there.

How the P3 runner shares this repository with production (its own event types, and its own API origin per dispatch) is ruled before `worker-dispatch`, not here.
