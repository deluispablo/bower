# Technical-lead decision TL-P2-2026-10-06-18: a stale hashes.json after a rejected move

Lead: Claude `Planificador`. This answers M4 from the O4 U2 review. Adopted revision stays `2026-10-05-contracts-2`, and contract B is unchanged.

Accepted as a documented limit, the simplest answer for a rare case. B fixes the text of `.bower/hashes.json` in the manifest before any effect. So when a move is rejected, the dependent hashes write is rejected too, and `hashes.json` stays as it was until the next run.

- **Nothing is lost.** The report does not claim the write, and the rejected items stay visible in `setAside`.
- **The worst case** is that exact duplicate detection misses one copy until the next run. The person may then see a duplicate.
- **The next run heals it, under one condition:** it recomputes `hashes.json` from the files actually stored, not incrementally from the stale file. If the planner does not already do that, add it to U2's rework.
- **Rejected alternatives:** a fallback "hashes of the moves applied" inside the manifest, and a separate write after reconciliation. Both add mechanism for a rare, harmless gap.
