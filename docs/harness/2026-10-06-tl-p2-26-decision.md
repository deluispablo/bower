# Technical-lead decision TL-P2-2026-10-06-26: what the note-edit contract left open

Lead: Claude `Planificador`. This answers four points from the `note-edit-contract` implementation (B.2, TL-P2-20 as ratified).

- **A. A separate v2 reader: accepted.** `parseRunManifestV2` is a separate reader. The v1 reader keeps refusing v2, and the v1 `Effect` and its consumers stay untouched. Two new refusal reasons are added: `edit` (a v2 rule) and `version` (a version above 2).
- **B. `rules-wording` layout: accepted, with one ordering rule.**
  - Adds are processed in ascending `since` order, each inserted at the top, so the newest ends first, as ratified.
  - Removals come before adds.
  - `ruleLike` dedupe compares against both the wording and the "You wrote" words.
  - A missing `## Rules` section is appended as `eol` + `## Rules` + `eol` + a blank line + the rules.
  - When there is no blank line after the heading, rules go right after it and none is added.
- **C. Archive→move/create dependencies: no contract change.** The guard checks archive→edit through `recordIds`. The planner guarantees archive→move/create, and the consumers' tests prove it: `b-path-merges` and `o5-saved-link-note` each include a rejected-move fixture whose record stays. Adding record links to `move`/`create` or a `kind` to `CapturedJournal` is not worth a contract revision for a fake-only planner invariant. Reconsider if a P3 consumer needs it.
- **D. The R3-1 blind spot: accepted as a documented limit.** A faulty splice that only drops a blank line inside a legacy Timeline passes the re-parse check. That region is Bower's and holds no meaning in blank lines. R3-2's byte-exact fixtures already catch such a regression in the implementation, so no independent recomputation is required.
