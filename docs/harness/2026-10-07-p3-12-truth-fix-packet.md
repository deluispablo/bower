- **Acceptance contract:**
  - **I1. Never say changes were made when none were.**
    - The runner sends `saving` only when the run's chain holds at least one applied outcome, and only after "effects done, report pending" is committed to the chain. This also fixes the review's minor: `saving` was posted before the commit.
    - With no applied outcome, a run that cannot save its report ends `failed` with `The tidy-up stopped before changing anything. Try again.` So does a run that hits an uncaught error. Use the existing `B_FAILURE` text, shared rather than copied.
    - After an applied effect, an uncaught error follows the same rule: the run goes to `saving` (so past the ceiling it says changes were made), never to the nothing-happened sentence. Wrap `runTidy`'s token → operations → barrier → status in that one rule.
  - **I2. Status after a restart.**
    - The Worker's 409 `stale-report` body carries its current `{ seq, phase }` (contract row updated in the same change).
    - On a 409, the runner resends once with that `seq + 1`. If the phase is already `done` or `failed`, the run is finished: it sends nothing more and does not claim a different outcome.
    - A refused `done` is never swallowed: if the resend is refused too, the runner throws, so the job fails visibly.
    - When `last-run.json` already shows this run done, the runner reads it back (`md5Checksum`) and commits `done` to the chain before it sends `done`.
  - **I3. Dispositions are recorded.**
    - Before `last-run.json`, the barrier writes `.bower/runs/<run_id>/dispositions.json`: one line per manifest item, journal lines included, each `filed`, `set aside` or `waiting`.
    - It is written with the fenced create or update and read back like the other report files.
    - `pile-disposition.ts` is unchanged.
    - A redispatch that finds the file already there leaves it as it is.
