## Entries: ten proposed, grouped into seven

Applying the owner's simplest-approach rule, the coordinator registers:

1. **`b-path-one-snapshot`.** `planRun`, `captureOf` and the reader plan from one listing. This removes the readiness and sending legacy reasons and the race halves.
2. **`b-path-asked-question`** (see Q1).
3. **`b-path-capture-reads`.** This joins proposals 3 and 5:
   - in a declared pile, only the file bound to the context key is the pile note;
   - context bytes are read once, and the digest and the decoding (fatal, `ignoreBOM`) both come from those bytes.
4. **`b-path-capture-holds`.** This joins proposals 4, 6 and 7. Each item that cannot be recorded or verified is held or left uncaptured, never sent to legacy:
   - **Names the manifest grammar refuses** (C0 or DEL, `\`, `..`) are held with the Q4 reason.
   - **A member whose digest cannot be checked** holds only its pile, with not-checked (TL-P2-08 (a)).
   - **Journal records that break the grammar** stay uncaptured with one `BowerError` (TL-P2-23 §3). That covers a C0 character, more than 1024 bytes, and the lone-surrogate request side finding.
5. **`b-plan-guard-refusal`** (see Q2).
6. **`running-scenario-on-b`:** `?scenario=running` starts its run on the B path.
7. **`legacy-runner-write-removal`:**
   - `runs` is required;
   - the legacy write path is removed;
   - legacy records stay readable.

`empty` and the dead journal branch are removed inside `o5-no-legacy-run-path` itself.

## Answers

- **Q1. (a), and B already requires it.** Contract B says question rows must equal the validated `questions.json` entries written by required applied operations. So the run's question is written by B's `questions.json` write, and the row is grounded by it, with `askedAt` = `requestedAt`. Dropping the scripted question would remove a capability.
- **Q2. Approved.** An internal guard refusal before admission reuses "The tidy-up stopped before changing anything. Try again." It also logs a `BowerError` to the console.
- **Q3. Left to P3, with a P3 note.** Drive fills `md5Checksum` and `sha256Checksum` only for binary content, never for Google Docs, Sheets or Slides ([Drive API files resource](https://developers.google.com/drive/v3/reference/files)). The P3 runner needs its own rule for native Workspace members, for example identity and `modifiedTime` instead of a digest. The fake cannot produce such a member, so nothing is needed in P2.
- **Q4. A name Bower cannot record.** The reason is "Bower can't file something with this name. Rename it in Google Drive, or remove the pile.", with Remove and no Try again.
- **Q5. Yes, both.** `o5-no-legacy-run-path` depends on `running-scenario-on-b` and on `legacy-runner-write-removal`. TL-P2-06 §1 keeps legacy only for reading records. The demo world's own run (`world.ts`) is outside O5: the demo is an in-memory illustration, not the fake stack.
