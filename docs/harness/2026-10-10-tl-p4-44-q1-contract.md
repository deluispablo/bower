# Technical-lead decision TL-P4-44: the Q1 contract (questions that don't block)

These are the rulings on the 10 questions in Codex's Q1 preparation draft (p4-q1-prep a1aa9cb5, `2026-10-10-q1-prep.md`). The draft is accepted as the base, with its promises P1-P9, its reds and the signed Q1b rows. It follows TL-P4-40 (2), TL-P4-43, the owner-approved spec (claude/design 2497e828) and the owner's principle of designing for normal use: today's mechanisms are widened, and no new mechanism is added for rare cases.

## Split

Q1a is too wide for one escalated entry (about 50 files across app, Worker and runner), so it is split in two. Both are escalated, and they run one after the other.

- **Q1a: stored answers.** Options, the widened answer, rounds, the pile projection and the continuation. It starts after C05 integrates.
- **Q1c: live publication.** Questions in the run status, merged by `vault.questions()`. It starts after Q1a.
- **Q1b: the UI** (Q-UI-1, -2 and -4, ui: true). It starts after Q1c, with the signed rows and the designer's check.

## Rulings

- **Q1. Options.**
  - There is one option action kind now: `file-to`, which files the waiting item into an existing folder id. Options appear only when the script has 2 to 4 candidate folders that the planner already sees. The model picks among those ids and words the question; it never makes an id or a payload.
  - The action is stored with the question in questions.json when it is asked. The answer carries only the option id, and the runner resolves the action from its stored question. A label is never used to resolve anything.
  - A legacy yes/no question keeps its meaning and has no stored action. State and pair questions are unchanged.
  - The `note` kind (which note) is not in Q1a. See Q6.
- **Q2 (Q1c). Publication point.**
  - A question is published once the run's plan is persisted, before its effects run. This is the first durable point, so a crash cannot lose the question's action. There is no per-item streaming from inside the model reply.
  - The runner's status report carries the full snapshot of this run's open questions, which replaces the previous one: at most 10, each within the existing question bounds, inside the existing 64 KiB body. A change raises the Worker's revision and leaves phaseAt alone. The existing attempt, seq and ticket fences apply.
  - `vault.questions()` merges the snapshot with questions.json by question id and askedAt, and the Drive copy wins once it exists. Answered askings are filtered through the journal as today, so an old snapshot cannot bring one back. The vault emits on a run-status change, so Home refreshes.
- **Q3. Rounds.**
  - A round is a newly written asking for an inbox subject, meaning a thing or a pile. Delivery repeats, model retries, redispatch, failed saves and a re-run that leaves the same question open do not count.
  - After the second asking's answer, if the item still has no place, it is marked exhausted. It is never asked a third time, and it stays untouched in the inbox with the sentence.
  - Counters and exhausted subjects live in questions.json, keyed by the existing subject identity (dedup and reupload hash included). They survive the card's removal.
  - **A change to the pile's words resets the counter.** The sentence tells the person to do exactly that, so it must work. Moving the item out of the inbox also ends it.
  - The cap covers inbox subjects only. State, pair and folder questions keep their existing re-ask.
- **Q4. The continuation's scope stays today's answer scope.**
  - An answer about a thing or a pile starts the existing subject-scoped run (answer-loop.ts:34), which takes that pile. Its clear siblings were already filed by the first run, so normally only the waiting items remain. Anything the person added to that pile meanwhile is the person's own item with the same words, and is handled like any item.
  - Journal admission stays as today. Answers that arrive during a run are batched into the Worker's existing single run after it ends (person.ts:688).
  - There is no frozen member list and no lineage store. B12 adds what it needs when it lands.
- **Q5. The answer line.**
  - The journal answer value widens additively: `true`, `false`, `{ option: id }` or `{ text }`, keyed by question id and askedAt, which is the asking identity. Old yes/no lines read as before.
  - The text is trimmed and must not be empty. It is at most 1,000 characters, line breaks are allowed, and other control characters are refused. The Textarea enforces the same 1,000-character limit, so nothing is cut silently.
  - Conflicting answers keep today's rule: the later record wins. There is one continuation request id per asking, as today.
- **Q6. Which note: not in Q1.** Q1 builds the general option contract. `c05-which-note` stays a follow-up after C05 and Q1a (TL-P4-32 (4) and addendum 2). It adds the `note` kind, bound by settleRequest to the original request and source, and only when the script's match list has 2 to 4 notes. With more matches, the existing "More than one note matches" row stays.
- **Q7. Provenance.** Confirmed as recommended. A text answer counts as the person's words for that subject only: it reaches the continuation as that pile's words, never as a global rule. An option is consent for its stored action only. Document and summary text never widen either. This is carried as typed data, never as prompt wording.
- **Q8. Quota and budget.** Confirmed. Each continuation counts one quota unit and has normal run budgets. Publication and replays count nothing. There is no extra model call to ask a question or to wrap an answer. On a quota refusal, the answer is kept, today's failed toast is shown, and no round is counted.
- **Q9. A UI consult to the designer** (sent by the lead). The lead's reading: "Something else…" also shows under an inbox yes/no question, since the owner's question was what happens when the answer is neither. When the last card in the sheet goes, focus moves to the sheet's title. Cards are shown in asking order. An answer removes the card everywhere, because there is one data source. Any change that is new behaviour goes back through the designer to the owner.
- **Q10. The pile projection.**
  - The listed and full Pile gains an additive `question?: 'waiting' | 'exhausted'`. The vault derives it from questions.json plus the open questions, through the shared subject policy. There is no new store.
  - Waiting wins over exhausted. The existing upload, error and readiness lines win over both.
  - The marker clears when the pile's words change or the item leaves the inbox.
  - B3's hot consumes the same projection.
