## Verdict: BLOCK (1 Important)

### Important 1: a long note name makes the public snapshot invalid, and the run fails before any effect

- `src/data/contracts/questions.ts:49` (`isQuestionSnapshot`) caps a question's `text` at 200 characters.
  `runner/src/status.ts` `publishQuestions` throws `BowerError('unknown', 'Bower could not share its questions.')`
  when the check fails. It is called from `onPlan` (main.ts:297) and the recovery path (main.ts:260), i.e. before effects.
- The 200 cap is the model-authored bound (`runner/src/claude.ts` ASK). The scripted planner's questions are not bounded.
  `STATE_ASK_AGAIN` (questions.ts:195) is 129 characters plus the note name, so a name longer than 71 characters
  gives text over 200. The consent variant (scripted.ts:1652) also embeds two names. `.bower/questions.json` accepts
  these (`layout.ts` `question` has no length rule), and before Q1c such a run succeeded.
- Reproduction: a note whose name is over 71 characters with an edited Current state, a granted re-ask. The planner
  makes `reasked` with `STATE_ASK_AGAIN(name)`. `plannedQuestions` returns it, `publishQuestions` throws, `tidy` ends
  the run failed with nothing written. The Worker would also refuse the same body (400) if it were sent.
- This breaks the contract line "a count never fails a run" in spirit, and the Q2 promise that publication is
  additive. A bound mismatch between the planner and the snapshot must not stop the run.
- Fix direction (lead rules): publish a card the Worker accepts without changing the stored text (e.g. fit text for
  the snapshot only, or drop an unpublishable card from the snapshot and log), never throw before effects.
- Missing test: `q1-live-question-long-note-name-publishes` (runner main entry, state re-ask for an 80-character name,
  run reaches done, snapshot carries the card or omits it, questions.json unchanged).
