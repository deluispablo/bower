## Evidence boundaries

No network research or model calls. The local standard is Bower's existing structured intent and its shared planner, not another writer. The local specification preserves questions over stored material and permission-aware enrichment (`docs/specs/2026-10-04-who-does-what.md:7`); the Worker contract already persists requests and their report rows (`docs/specs/2026-10-04-worker-contract.md:85`). Existing library/runtime schema and persistence are reused; no external standard is claimed to have been verified offline.

There are two existing boundaries, and they are not equivalent:

- The Claude reply is a strict `tidy-intent` object with things, notes, lines, states, asks and keep (`runner/src/claude.ts:800`). It has no query-answer field. Its context contains piles, shown notes, folders, rules and answers to Bower's questions, not the person's request text (`runner/src/claude.ts:323`). `answers` there means yes/no to Bower's questions (`runner/src/claude.ts:302`), not C09 answers.
- The planner already has `RequestPlan` and `Decisions.request(text)` (`src/data/spine/scripted.ts:198`, `src/data/spine/scripted.ts:247`). The demo provider supplies it (`src/data/demo/script.ts:58`); `modelDecisions` does not (`src/data/spine/scripted.ts:257`). Without that callback, request journal records wait instead of being archived as answered (`src/data/spine/scripted.ts:467`). The stored answer is `Request.done` (`src/data/contracts/types.ts:182`) written by the existing requests operation (`src/data/spine/scripted.ts:1770`).

Thus an empty Claude reply can prove a request remains pending, but cannot produce any of these positive answers. An invented `answers`, `requests`, `citations` or `done` reply key would be refused, not a usable scripted proposal. The exact existing-boundary objects below are explicit about that limit. A lead-approved connection of query input/output to `Decisions.request` belongs to the C09 slice, not a silent preparation edit or test-only persistence path.

Shown notes are Bower-owned or folder hubs, capped at 12 notes and 24,000 characters overall, 4,000 per note (`runner/src/claude.ts:157`, `runner/src/claude.ts:405`). Stored original text files/PDFs are not fed to the model by that note reader; byte extraction in `shownOf` is for admitted inbox things (`runner/src/claude.ts:351`, `runner/src/claude.ts:374`). Names of stored files alone are not their content (`runner/src/claude.ts:387`). Read eligibility for a person's own note is a product decision distinct from permission to edit it; the C05 ruling cannot be assumed to grant a general C09 read contract.

Lines require a shown note and a citation to a filed thing or words-only pile; they contain no links themselves (`runner/src/claude.ts:912`, `runner/src/claude.ts:833`). Authored thing-note bodies can link known names, but name existence does not establish that a claim is supported (`runner/src/claude.ts:720`). Neither is a substitute for a read-only answer about stored material.

The scorer can compare whole starting files, inspect answer-file substrings and bound report rows (`runner/src/corpus.ts:258`, `runner/src/corpus.ts:262`, `runner/src/corpus.ts:282`). `report.requests` asserts the request text, not its answer (`runner/src/corpus.ts:315`). `linksResolve` skips `.bower/` and unchanged notes (`runner/src/corpus.ts:276`), and its resolver accepts matching basenames (`runner/src/corpus.ts:229`). It therefore does not check links inside `.bower/requests.json`, exact source identity, source reads, or claim support. The new JSON assertions are useful structural constraints; rubrics and future driver assertions carry the rest.

## Open product questions for the lead and designer

Six questions; none decided by this draft:

1. **Lead:** What is the minimum approved C09 query contract at the existing intent boundary: which admitted request identity/text is shown, and how does a proposed answer reach the existing `Decisions.request` without a second writer?
2. **Lead + designer:** Which stored originals and person-authored notes may a query read, and how is that read scope communicated? Reading must not imply ownership or permission to edit.
3. **Lead + designer:** Should an answer link both the compiled note and original, or always the original for each supported claim; what labels and optional section/page locators should open them unambiguously on phone and desktop?
4. **Lead + designer:** How should stale summaries and disagreeing originals be explained, and should an answer offer a separate update action? The fixtures propose preserving material while answering, not automatic repair or conflict resolution.
5. **Lead + designer:** When evidence is missing, unreadable or cut, should Bower complete an honest limited answer, ask for more material, or leave the request pending? What visible distinction separates those outcomes?
6. **Lead + designer:** Do short answers stay in “What you asked”, and when does a long stored-material answer become a C08 authored document? How should reload/replay and a fresh query after source changes be presented?
