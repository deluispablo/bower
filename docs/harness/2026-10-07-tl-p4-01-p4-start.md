| Entry | Agent, reason | Acceptance contract |

| `p4-corpus` | `bower-implementer`. Test data and a scorer, in existing patterns | A synthetic corpus under `harness/corpus/`, with at least two cases per capability from C04 to C11, plus C13 and C15. It reuses the original's `agent/bench/cases` where they fit, and the P2 scripted journeys' inputs. Nothing personal. The scorer passes on the scripted provider's outputs for the C04–C11 cases it already covers, and fails on an assertion when an expected file is removed. |
| `claude-provider` | `bower-escalated`. A new external boundary and data safety | A `ClaudeProvider` behind the existing semantic-provider interface. It runs headless Claude Code in the runner (`claude -p`, JSON output), authenticated by `CLAUDE_CODE_OAUTH_TOKEN` from the instance repository's secrets, under the original's permission policy (`agent/claude-settings.json`): no Drive tool, no write tool and no shell. It receives the prepared context and returns structured operations only, which the spine validates. A malformed or out-of-schema reply becomes a truthful failure, never a write. The model and turn cap are set by environment (start: Sonnet, the original's `DEFAULT_MAX_TURNS`). Tests run on recorded replies, using the same contract fixtures as the scripted provider. The token is never logged. Live use waits for the owner's secret. |

**Research first:** both packets cite Claude Code's headless and GitHub Actions documentation, and the original's `run.sh` and prompts, before designing.

## Addendum: speed against the original (owner request)

The owner asked for every run time to be compared with the original's recorded times. They are in [p4-speed-baseline.md](p4-speed-baseline.md): 6 min 38 s before the original's speed work, and 44–90 s for the agent step after it (bench cases 1–5).

The P3 scripted run already takes 2 min 07 s with no model, so the runner's own overhead is the first risk:
- **`p4-corpus`** includes the original's five bench cases unchanged.
- **`claude-provider`** logs one timing line per run, split by phase.
- **New entry `runner-overhead`** (`bower-implementer`), in P4-2. It profiles a scripted run phase by phase and cuts what is not needed. Likely candidates are the job set-up, the Drive round trips per operation, the checkpoints and the attempt checks, which can be batched where safety allows. The target is under 60 s end to end with no model. Safety comes first: every cut is checked against the recovery tests.
- **Every live run** is recorded in the baseline's table.
