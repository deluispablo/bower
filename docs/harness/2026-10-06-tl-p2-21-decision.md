## Ruling: option B, no report row for piles a run did not take

A readiness-blocked pile is not ready, so B does not capture it, and that is correct. On the B path, the report describes only what the run captured and did. It does not mention held piles.

The reason and its action live where the person looks: on the pile in the Inbox (`pile-set-aside-reason-visible`, TL-P2-11 and TL-P2-19). That place is authoritative and stays current; a report row would be stale after the next run.

- **This amends TL-P2-06 §6.3 for the B path only.** Legacy runs keep their `setAside` rows until the legacy path is gone.
- **Only held piles waiting.** `process()` admits nothing and answers the existing 409 `nothing` with "Nothing in the inbox is ready yet." No manifest is written, and there is no zero-operation run.
- **Option A is rejected:** it is a contract revision for information the Inbox already shows. **Option C is rejected:** it would ground a row on an unrelated operation.

With this ruling the held-pile half needs no contract change. So `b-path-held-piles` may close as one entry; splitting it is the coordinator's choice.
