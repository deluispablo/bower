# Technical-lead decision TL-P2-2026-10-06-13: one active session per person

Owner ruling, 2026-10-06: limit use rather than make concurrent sessions perfect. Bower blocks second sessions the way WhatsApp Web does. Two sessions of the same person are unlikely in normal use, yet they cause a large share of P2's concurrency defects. Adopted revision stays `2026-10-05-contracts-2`. This decision narrows C14 and two journeys (see P2_ACCEPTANCE), and adds one P2 entry and one P3 obligation.

## Behavior

- **One session at a time.** A person has one active Bower session across all their tabs, windows and devices. Opening Bower anywhere else never takes over silently. The new place shows "Bower is open in another window." with the button "Use here".
- **Taking over.** Choosing "Use here" makes that place active. The previous place then shows the same screen with its own "Use here", and from that moment it writes nothing.
- **Signing in** on a new device is the same: it asks before taking over.
- **What a blocked session stops.** It makes no Drive writes and does not flush the journal outbox. It sends no uploads and starts no tidy-up. It shows nothing that could go stale as if it were current.
- **Work left on a device** stays there: its outbox lines and pending uploads, keyed by account and folder as before. It continues when that device is used again ("Use here"), never from another account.
- **Offline.** An offline session keeps working into its outbox. On reconnecting it checks the session before flushing. If it lost the session, it shows the block screen, and its outbox waits.
- **A tidy-up belongs to the person, not to the session.** An admitted run keeps going in the service and shows in whichever session is active. The session check fences the app's own writes. It does not fence the runner's effects. In the fake, the page-local legacy runner stands for the backend: being blocked does not stop it. O4's service already removes that dependency on the page.

## Mechanism (reuse before building)

- **Within one browser:** detect other tabs at once with `BroadcastChannel` plus the Web Locks the app already uses. A tab holds the active lock; a new tab asks before it takes the lock.
- **Across devices:** the Worker holds a per-person session lease with an increasing epoch, so a fencing token decides which session is active. In P2 this is the fake Worker. In P3 it is the real Worker, recorded as a P3 obligation. The lease adds no field to RunWire. It is a small session call next to `me()`.
- **Fencing.** Every app write path checks the current epoch before it acts, and so do the outbox flush, uploads and `process()`. A real Drive write already in flight when the session changes cannot be recalled. That is accepted, given how rare this is, the same way as R1.

## Consequences for P2

- **New entry `single-active-session`**, early: it simplifies the rest. It covers the fake lease, tab detection, the block screen, fencing of app writes, and e2e on demo and fake. Two pages: the second asks first, "Use here" moves the session, and the first then writes nothing. It uses the existing screens and components.
- **C14** no longer requires two app sessions editing at the same time. It requires:
  - the takeover and fencing above;
  - the runner and external Drive editors changing things while the app is open;
  - refresh/invalidation, stale replies, malformed backend files and journal recovery;
  - recovery from another device after a takeover.
- **Registered entries** whose only purpose is two app sessions editing at once are marked superseded by this ruling with the coordinator's note, not passed. Working code that already exists for this, such as the cross-tab outbox lock, stays where it does no harm. Do not spend new units on it.
- **`upload-queue-persistent`** drops the fixes that only matter for two active tabs: a re-add or discard in another tab. It keeps every protection against duplicates after a reload or a lost reply (reserved IDs, read-back).
- **Unchanged:** O4's recovery without the originating browser; lost replies; readiness against Drive changes made outside Bower; R1's accepted limitation with external writers.
