## 2. Trusted recovery with RunWire unchanged

- **Recovery belongs to the service.** No new payload, phase, public WorkerApi method or RunWire field. A returning authorized client asks for recovery only implicitly, through calls that already exist:
  - `status()`;
  - or `process()`, whose same `requestId` or single-active-run rule returns the admitted run rather than admitting a new one.

  The client never claims a run or executes from a manifest. The fake run service decides from its control record. Recovery starts when:
  - the head is not terminal;
  - there is no unexpired claim;
  - every outstanding dispatch is reconciled.

  The service then issues a new `attemptId` with a strictly greater `epoch`. Effects and callbacks from a stale epoch are refused at the fake mutation boundary. An internal method on the service is allowed as a test seam; it is not part of WorkerApi.
- **Identity stays fixed.** The run keeps the same `runId`, `requestId`, manifest and capture. Recovery never calls the planner. It reconciles `possible-effect` outcomes against stored evidence, then dispatches only what was never dispatched, in order. It rebuilds the report from the durable `reportPlan` and outcomes. While recovery runs, clients see `saving` (or the head's earlier phase).
- **Authority.** A client may recover only runs in its verified binding and root. A revoked or other-scope client gets a refusal, and nothing takes effect.

## 3. Confirming the terminal view

Follow B's order and add no field to Control or Checkpoint:

1. The report record is confirmed by reading it back and comparing its hash.
2. The checkpoint with the report `published`.
3. The consumed dispositions, confirmed.
4. The `done` checkpoint, with the control head advanced.
5. The `.bower/last-run.json` v1 view is written with the modifiedTime it read.
6. The view is read back.

**Public `done` is derived, not stored.** The service exposes `done` only when the head is a `done` checkpoint *and* the stored view matches the exact body expected for that run. Until then the public phase is `saving`, and recovery rewrites the view. The service may cache a successful match in memory. The cache is never authority: after a restart, the service reads the view back again.

**The view body is deterministic.** `finishedAt` is the `phaseAt` of the `done` checkpoint. So a rewrite is byte-identical, and a reply lost after the write reconciles by comparing that exact body. If the view belongs to another run or does not match:

- the run stays `saving`;
- the service logs a `BowerError`;
- the service never overwrites a later run's view;
- the service never trusts a mismatched view as confirmation.

## 4. Ratified: bound on the journal `recordId`

`CapturedJournal.recordId` must be non-empty, contain no control characters and be at most 1024 UTF-8 bytes. Punctuation is kept. This is the same rule as DriveId, and contract B's "bounded" now means this bound. Journal producers must never emit a longer id. The manifest candidate as implemented and reviewed complies.

## 5. Checkpoint chains are monotonic

Within one run's chain:

- `revision` increases by exactly one, and `previous` names the prior record.
- The phase never goes back, in the order `queued` < `reading` < `writing` < `saving` < `done`. It may repeat the same phase.
- `failed` may follow any phase except a terminal one, subject to the existing honest-phase rule. Both `done` and `failed` are terminal: nothing follows them.
- The report state moves only forward: `not-ready` → `pending` → `published`.
- A `pending` hash and body are fixed once written. The step to `published` keeps the same hash, and `published` never goes back.
- A recovery attempt continues from the head's phase and report state; it never resets them.

Register this as its own checkpoint-guard entry. It is not urgent, but it must land before O4's recovery reads a chain it did not write itself. O4 must not rely on the current guard accepting a chain that goes backwards.

## Owner rulings received 2026-10-06

Given directly by the owner to the lead; recorded in the WORK_PLAN decision register.

- **R1, same-file conflict: simplest solution.** Normal use of the app makes this very unlikely. Keep the existing check of the modifiedTime read before every content write. A detected conflict never overwrites, and the person's edit is kept. The race with a non-cooperating external writer between that check and the write (R1-OBS01) is an accepted, documented limitation, not a blocker for P2 or P3. Save a copy (TL-P2-05) is not adopted. Do not build a synchronization layer, and never call the write atomic.
- **Offline reading: simplest solution.** There is no in-app offline note reading. Notes are plain Markdown in Drive, so they stay readable offline through the person's own local Drive sync. Offline, the app says so truthfully and queues changes as today.
- **Uploads in progress are kept.** The selected bytes stay on the device until Drive confirms the upload, and continue after a reload. A storage failure is disclosed, and same-session retry stays mandatory. This makes D02 a required P2 entry: on a reload, upload from the retained bytes, and reselect with hash matching only when those bytes are gone. Use TL-P2-05's pre-generated-ID recommendation for R4.
- **Reuse.** Features that already worked in the original Bower app are reused, code included, when they fit the new contracts and pass the same tests and review. For new work, first use an existing library, official sample or repository; record the source and a one-line reason in the entry.
