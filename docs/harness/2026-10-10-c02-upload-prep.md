The protocol and device store already resume an individually queued upload. The remaining normal-use gap is the boundary between saving a whole pile and putting **all** its selected files into that queue. Folder declarations without a visible anchor are excluded from discovery, and Home has no orphan count. Sign-out also needs a ruling: the current implementation follows TL-P2-07's retention exception, whereas the current AGENTS hard rule says to forget device state and names only the journal outbox as staying.

This preparation records candidate defects and contract gaps here for the lead to rule and the coordinator to register through the defect workflow before assigning fixes. It does not fix them where they show.

## Standard solution and reuse

No network was used. Research here uses the in-worktree protocol implementation, protocol tests and recorded R4 provider evidence. The official references below are inherited references, not newly fetched or checked on this date.

Google's [resumable upload guide](https://developers.google.com/workspace/drive/api/guides/manage-uploads#resumable) is the standard: save the session URI returned in `Location`; send an empty PUT status query with `Content-Range: bytes */TOTAL`; on **308 Resume Incomplete**, use the server's `Range` (inclusive last byte + 1), with no Range meaning zero; on 200/201 reconcile completion. The URI is sensitive and must never appear in logs. Sessions are temporary (the guide describes a one-week lifetime); an expired session needs a new session, not a new logical file. Do not predict completion or expiry from the saved offset or elapsed time alone. The current adapter treats 404/410 as expired.

Use [Drive pre-generated IDs](https://developers.google.com/workspace/drive/api/guides/manage-uploads#pre-generated-ids) through the existing write-once keeper: persist the reservation before any create, reuse it after session expiry, and check the existing file on an ambiguous answer or 409. Never retry by a new filename or a new ID just because a reply was lost.

Local evidence: `src/data/drive/drive-http.ts:342` opens the session, `:364` queries status, `:384` interprets it; `src/data/drive/resumable-upload.ts:122` queries a saved session and `:131` bounds restarts. `docs/harness/2026-10-07-tl-p3-12-r3-r4-and-p3-6-close.md:67` records R4's 10 MiB upload, reload after 8 MiB, server offset, matching checksum and one file; `:101` records reserved-ID reconciliation. This proves provider premises, not whole-pile byte retention in the app.

The original app was **not** read outside this worktree. Its recorded reuse evidence is `docs/harness/2026-10-06-old-app-reuse-map.md:7` (D02): original `app/src/upload-queue.ts:61–275` resumable protocol and injectable transport, `:285–376` browser transport, `:530–922` queue with session/offset persistence, confirmation-before-deletion, one-tab sending and storage fallback; `app/src/cache.ts:520–596` IndexedDB records. Current adaptations already record FSL-1.1-MIT provenance in `src/data/upload-queue.ts:18` and `src/data/upload-store.ts:8`. Reuse these adaptations, not another queue. The map's `:8–9` explicitly rejects the original's silent omission of missing piles; only wording/principle is reusable there.

Existing libraries suffice: `fake-indexeddb`, `fast-check` and `@noble/hashes` are installed (`package.json:26`, `:52–53`). No new dependency is proposed.

## 1. Checkable promises

### Uploads resume after reload

“Reload” means a new page/queue/store instance after a pile has been submitted to the Inbox. Selecting files in an **unsaved Add draft** is a different boundary: `e2e/qa6.spec.ts:222` and `e2e/qa9.spec.ts:68` deliberately ask for those draft files again. Do not reinterpret those tests as failed resumable uploads.

| Part | Proposed observable acceptance |
| --- | --- |
| Save boundary | Once `addPile` resolves and Add reports the pile saved, every submitted Blob has either a committed device record and bytes, or an explicit memory-only storage outcome. Holding the first transfer must not prevent later members being retained. A save must not claim durable retention before its transactions finish. |
| Same file | Scope is account + root folder + declaration + member key + SHA-256, never filename. Retained bytes resume without another picker. Lost bytes use existing hash-match reselection; a same-name or same-size different file is refused. |
| Offset | Query Drive before sending from a saved session. Resume at Drive's offset even when the device's confirmed offset lags a lost chunk reply. Use aligned chunks (256 KiB except the last); do not equate progress UI with confirmed bytes. |
| No duplicate | Persist one reserved ID before opening a session. A lost final answer, reload or expired session results in one logical file with that ID and matching content. An already arrived file moved elsewhere is accounted as arrived, never recreated in Inbox. |
| Expired session | Reopen using that same ID. Keep `MAX_RESTARTS = 2` per try; exhaustion keeps bytes and the existing retryable error, without an automatic loop. Permanent refusal follows write-once's existing release rule. |
| Completion | Delete device bytes/progress only after Drive confirms the intended content. A transient status/read failure keeps pending evidence. Discard/Remove and account deletion are deliberate exceptions, through existing withdrawal/forget mechanisms. |
| Sign-out | Proposed current-hard-rule reading: stop/fence sends and remove pending upload bytes and metadata for that account in every folder; leave journal outbox lines alone. Do not delete Drive files or declarations. This conflicts with TL-P2-07 and requires Q1 before an implementation packet. Reload/dispose is not sign-out. |
| Other tab | Existing Web Lock serializes the account/folder queue; the session lease fences writes across places. Blocked memory-only files remain paused in that page (TL-P2-24), and Use here resumes them. A competing tab takes over at server offset. Purge/discard must not be undone by a late device write. |
| Another folder/account | A new context cannot list or send the old pending queue. Root IDs and account hashes identify the scope. Opening another folder is not permission to migrate old bytes. Under the proposed sign-out policy, signing in again does not automatically resurrect removed uploads. |
| Storage limits | Preserve the existing 200 MiB durable-file limit, persistence request, quota check and memory fallback. Browser eviction, denied storage and another device honestly require reselection; never promise automatic resume when there are no bytes. |
| Changed destination | Do not create a replacement folder or redirect into Inbox on a missing/changed parent. Reconcile an arrived reserved file first; otherwise retain and hold the pending member until the existing destination can be checked. See Q6. |

### Orphan-pile count (app side)

Proposed definition for review: an orphan is a **distinct, valid declared pile in the current root whose intended Inbox anchor is absent and whose intended work has not all been accounted for**. Count piles, not members, declaration copies, failed HTTP requests or upload records. A loose single member not yet arrived is the loose form of the same rule. A folder declaration whose folder never got created is the folder form.

| Case | Proposed result |
| --- | --- |
| Valid folder declaration, no matching live anchor, unresolved members/context | One orphan, even with many members or identical declaration copies. Includes declaration written before a failed folder create. |
| Valid loose declaration, member absent everywhere and not intentionally removed | One orphan, whether bytes are retained here, lost here or exist on another device. A local queued row and its declaration are one pile. |
| Live matching anchor, one or more missing/changed members | An incomplete existing pile, not an orphan. Keep its existing per-pile reason. |
| All intended members accounted as consumed or arrived elsewhere; context settled | No orphan. Use validated disposition/member accounting, not the mere presence of a disposition stamp. Context-only declarations need Q4. |
| Deliberately removed/Binned pile | No orphan; preserve existing Bin/Remove semantics. A missing listing alone does not prove deliberate removal. |
| Matching anchor moved elsewhere in the current root | No orphan if that identity can be established; do not recreate it or infer identity by name. Outside visible scope or inaccessible: unknown, not definitely absent. |
| Unreadable, damaged, conflicting or foreign-root records | Never pretend an exact zero. Foreign-root records are excluded; unreadable/conflicting current-root candidates make completeness unknown and are logged. Identical copies dedupe; differing copies are not arbitrarily chosen. |

Recommended surface: one count in the existing **Home Inbox summary**, alongside the current waiting-things summary, derived from the same full-read snapshot. Orphans do not inflate the “Tidy up N things” readiness promise. No extra alert per failure case or new recovery wizard. Proposed copy direction, **not approved copy**: “1 pile needs your help” / “N piles need your help”; with incomplete evidence, a separate plain statement that Bower could not check all piles, never “Nothing waiting” as a claim that none need attention. Wording must not imply the person can repair a missing folder with today's file picker. Placement, zero/unknown treatment, navigation and actions are U1–U3 for the designer and owner under TL-P4-40.

## 4. Questions for the lead (7) and designer (3)

These are contract recommendations, not owner questions sent by this worker.

1. **Q1 — Sign-out exception:** Does TL-P2-07's “pending uploads stay through sign-out” survive the current AGENTS hard rule? Recommend applying the current rule: purge account-scoped pending bytes/metadata on accepted sign-out and auth expiry; ordinary page disposal keeps them. The journal outbox alone stays. State whether failed remote sign-out still forgets locally and how a local purge failure is reported. No silent console-only success for a privacy promise. Old queue/store comments must be corrected if this ruling changes. UI effect to designer.
2. **Q2 — Accepted save:** Is the resume promise for all Blob members after `addPile` resolves, even if the first has not finished? Recommend yes: await device staging, not Drive transfer, before the saved outcome; explicit memory fallback retains today's storage wording. Keep unsaved Add drafts outside this promise. Do not impose a new save-time bound here; lead carries the existing bound into the packet. Designer confirms saved/progress semantics.
3. **Q3 — Orphan definition:** Does “orphan” include loose declarations with no arrived member as well as folder declarations with no anchor? Recommend one general unanchored-declaration classification, deduped by pile/declaration identity within the root, and no count of incomplete anchored piles. Do not count every declaration left after tidy-up.
4. **Q4 — Retirement/context:** When members are consumed/arrived elsewhere but the folder is absent, is the pile retired, including a context-only pile? Recommend reuse validated `accountPile` disposition/digest facts plus the existing context-removal facts. Do not count an intentionally removed context or retired work; classify ambiguous context-only history as unknown until a precise read-only rule is specified. No change to disposition or brain contracts.
5. **Q5 — Missing capabilities/bytes:** What promise applies with no Web Locks, storage refusal or files above 200 MiB? Recommend preserve the limits and hash-match fallback; session fencing stays the one active-place mechanism. Automatic durable sending requires proven ownership; a rare unsupported browser may honestly hold/reload rather than introduce another lock scheme. Specify whether existing no-lock behaviour is accepted or needs a separately diagnosed entry.
6. **Q6 — Missing/changed destination:** Should reload recreate a vanished pile folder or send into another place? Recommend no automatic recreation, rename or move. Read back the reserved file; if it already arrived, never send it again. Otherwise hold retained bytes when the destination is missing/unchecked and report recovery facts. Use existing halt/session/write-once mechanisms; a broader restoration workflow is outside this app-side count preparation and must be separately ruled/designed.
7. **Q7 — Unknown count/API:** Can a count be exact when declarations or disposition reads fail? Recommend known count plus completeness, from the same cached full read. Unknown is not zero. Reuse the parser/query home and preserve existing stored v1 records. Reject a new persistent orphan table or per-screen discovery rules. Lead freezes the app-local `VaultSource` summary shape before E3 reds.
