# Technical-lead decision TL-P2-2026-10-06-36: a pile note in a format Bower refuses

Lead: Claude `Planificador`. This answers the finding behind `pile-note-format-visible`, and applies TL-P2-08 and TL-P2-11.

A pile whose note Bower refuses to parse stays listed in the Inbox. The causes are a future `bower_format`, a damaged boundary and invalid encoding. Such a pile is held from runs, and its note is read-only.

Retrying cannot change a format, so the reason offers Remove (recoverable, TL-P2-31) rather than Try again:

- **Unsupported version:** "This pile's note needs a newer Bower."
- **Damaged boundary or invalid encoding:** "Bower can't read this pile's note."

**Amendment (same day).**

- **A save refused while a pile's note is unread** uses "Bower could not read this pile's note. Try again." It is closer to the cause than the general sentence. Approved.
- **A plain pile note with text no record can carry** (a lone surrogate, which only happens in the fake) gets the `note-damaged` reason: "Bower can't read this pile's note." with Remove and no Try again. Retrying could never fix it.

**Second amendment (same day): a pile note that changed elsewhere.** This is the standard edit-conflict pattern. A refused save keeps the person's draft. While the draft still differs, one line shows above Save:

"This note changed elsewhere. It now says “{words}”. Save again to replace it with yours."

`{words}` is cut at about 80 characters, at a word boundary, with "…". The next Save is an informed overwrite.
