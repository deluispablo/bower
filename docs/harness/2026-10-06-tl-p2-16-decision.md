# Technical-lead decision TL-P2-2026-10-06-16: confirming O4 U2's choices

Lead: Claude `Planificador`. This answers the six choices the U2 implementer asked the lead to confirm, plus the known limit the coordinator reported. Adopted revision stays `2026-10-05-contracts-2`. Contract B, TL-P2-06 and TL-P2-10 stand.

1. **The fence pass-list counts as a trusted no-effect proof, in the fake only.** The fake owns the mutation boundary, so "this dispatch never passed the fence" proves nothing happened. Three conditions apply:
   - **Recorded with the mutation.** A dispatch's pass is recorded in the same serialized step as its mutation, before the effect. It survives a reload, so no crash can leave an effect without its pass record.
   - **Same outcome, sent again.** It is sent again only after its epoch is superseded. It goes with the same `dispatchId`, and the outcome stays `possible-effect` until the effect is reconciled; B does not allow a step back to `before-effect-refused`.
   - **A dispatch that passed** but shows no effect stays unresolved.

   This proof does not carry over to P3. Real Drive has no such fence, so P3 reconciles by evidence: reserved IDs and read-back.
2. **Dropping all claims on restore: accepted.** The epoch counter is persisted and never reset, so the next claim's epoch is strictly greater. Before a new claim, any outstanding dispatch is reconciled under point 1. A live claim expires after 300 s.
3. **The view hash recorded at admission: accepted, amended.** A publication may replace:
   - the view whose hash was recorded at admission;
   - or a view belonging to a run admitted *before* this one (for example, an earlier legacy run's late `done` retry), checked by the service's admission order or, for legacy runs, an earlier `requestedAt`.

   It never replaces a view from a later run. Otherwise one late legacy retry could leave a B run stuck in `saving`. Accepted too: the B path writes no intermediate views. Status comes from the service.
4. **Accepted.** A failed precheck before dispatch takes the outcome from `possible-effect` to `rejected` (conflict), with no dispatch. Dependents of an operation that was not applied are rejected without dispatch. The report puts the affected items in `setAside` and never Bins a pile whose moves did not all apply.
5. **The legacy list is accepted as this cut,** with one condition: every reason on it maps to a registered entry, and `o5-no-legacy-run-path` proves the list is empty except for reading legacy records. The coordinator checks that mapping. As far as the lead can see, these still need an entry:
   - piles blocked for readiness: they produce no effect, so the B path can hold them with `setAside`;
   - item name different from file name;
   - a destination that needs several new folders;
   - unreadable runner files.
6. **Accepted.**
   - `yourChanges` is absent from B reports, since the journal stays legacy.
   - `hashes.json` comes from the stored digests, without dot paths.
   - **Wording of the fixed failure sentence.** The honest-phase rule allows `failed` only when nothing applied, so the sentence should say so plainly: "The tidy-up stopped before changing anything. Try again." It needs no new field.

**The known limit is a defect.** In the fake, the runs state is saved right away and the Drive snapshot 250 ms later. A reload in that window leaves service records pointing at Drive effects that were never saved, which breaks "an admitted run survives its client". Fix it before U2 closes:

- write both in one snapshot;
- or always save Drive first, so the runs state never refers to unsaved Drive state.

Add a test that reloads inside the window.
