## Evidence boundaries

No network research or live model run was performed, as instructed. The local standard is already documented in the provider: headless Claude with bounded output, no tools/MCP and intent-only replies (`runner/src/claude.ts:3–30`). Its cited references are [Claude headless mode](https://code.claude.com/docs/en/headless), [CLI flags](https://code.claude.com/docs/en/cli-reference) and [settings](https://code.claude.com/docs/en/settings); these links were read from local code, not freshly verified. Recovery follows the existing write-ahead/checkpoint mechanism, whose local source names ARIES and SQLite WAL (`src/data/spine/engine.ts:7`). Reuse those mechanisms; the model never writes Drive and no case creates a second write path.

All three delivered cases are `covers: model`: they are acceptance snapshots and semantic rubrics pending deterministic fault/lifecycle proof, not claims that today's demo provider produces their outcomes (`harness/corpus/README.md:10`). The new `expected.json` files describe the successful later or recovered result for cases 1–2, and a single bounded-read result for case 3. They deliberately do not encode nonexistent status/fault keys. Loading a model case is not executing or scoring its lifecycle.

C05's original harness limitations are partly obsolete. TL-P4-28 addendum 1 accepted exact question counts, typed pair identity, between-run edits and scripted planner execution (`docs/harness/DECISIONS.md:314`). Current types also support later presses, replay requests, typed answers, per-press expectations, protected byte ranges and Drive properties (`runner/src/corpus.ts:37–64`, `:84–103`, `:120–156`). The driver already offers `runWithClaude`, a fetch wrapper and per-press execution on the same fake Drive (`runner/test/corpus-run.ts:66–91`, `:154–187`). `replySequence` binds `$file:NAME` to exact shown names, but wraps every object in a successful CLI result and repeats the same reply for correction within a press (`runner/test/corpus-run.ts:288–310`). It cannot express time cuts or a changing correction sequence by putting those fields inside intent.

C05 addendum 2 separated person-note policy from harness work (`docs/harness/DECISIONS.md:324`); the later addendum 3 rules on explicit requests to person-authored notes (`:352`). These cases use an existing Bower-marked note, make no new person-note policy and propose no state overwrite. The model may propose state through the existing gate; the snapshots do not freeze compiled state. `report-kept-your-change` is explicitly owed to C12 (`docs/harness/DECISIONS.md:96`), so it remains a proposed lifecycle case below.

C12 is not yet in `CORPUS_CAPABILITIES` (`runner/src/corpus.ts:20`). `loadCase` reads JSON by a TypeScript assertion rather than rejecting unknown capability strings (`:187–193`); the corpus capability test iterates that constant (`runner/test/corpus.test.ts:22–39`). No runner types are changed in this preparation.

### 1. Model failure, then the person's later retry

Start with the delivered note and notice. Script a terminal time cut through the existing ClaudeSpawn, not an empty successful intent:

```json
{"code":null,"stdout":"","stderr":"Synthetic model time limit.","cut":"time"}
```

This is a `ClaudeExit` object (`runner/src/claude.ts:102–113`), so no usable intent exists for that failed call. Also exercise `cut: size`, a turn-cap envelope and a nonzero error result as separate deterministic variants. Never sleep for the real 15-minute cap. Check one model call for each terminal failure, failed status, no content effects, notice and folder bytes unchanged, no bogus success report and request eligibility on the next press. If seeded prior last-run exists, it must not be passed off as this failure's result. `main` can return code 0 for a terminal failed state (`runner/src/main.ts:341`); inspect statuses, not only the process code.

For malformed intent, give two schema refusals and verify exactly two calls; separately give one malformed result followed by the valid intent below, verifying one correction and one successful plan. ## Open product questions for the lead and designer

Five questions remain; this draft makes no choice.

1. After a terminal model failure, what exact failure/retry control does Home show, and is the next action a fresh tidy-up or explicit replay of the failed request? What remains available after reload?
2. How should a person see partial confirmed changes while recovery is pending, and what can they safely press when an outcome remains unconfirmed or access has gone? Distinguish unfinished work from a placement question.
3. Where and in what words does the app disclose a cut/unread source or omitted note context? Is filing a clear-fit source without reading its appendix acceptable with that disclosure, and how can the person request the rest without a false promise?
4. What exact row and grouping implements `report-kept-your-change` when a confirmed earlier effect survives only as history and Alex has since moved/edited it? How does it differ from unconfirmed work and C13's partial undo?
5. What recovery ceiling or supported retry policy applies to model and tool failures, and how are turn/time/read limits distinguished from quota/cost limits? Existing constants are evidence of current bounds, not authority to invent a new product budget.
