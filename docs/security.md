# Security

How a Bower instance is meant to be attacked and defended. To report a vulnerability, see `SECURITY.md`.

## Threat model

1. **The operator is trusted.** They deploy the Worker and hold every secret (`TOKEN_ENC_KEY`, `SESSION_SECRET`, `GITHUB_TOKEN`, ...), so they can decrypt any stored refresh token and read every vault of their instance. This is by design, and users are told so in the privacy statement (`docs/privacy.md`).
2. **Users trust the operator**, and each other only as far as a household does: the Worker keeps one user from reading or changing another user's vault, run or settings, but nothing protects a user from the operator.
3. **Google shows an "unverified app" warning** once per user, because the operator's OAuth client asks for the full `drive` scope and is not verified (see `docs/decisions.md`). Users are told to expect it; it is not an attack.
4. **What the Worker stores (KV):** per user the email, the Google refresh token and the optional Claude API key (both AES-GCM encrypted with `TOKEN_ENC_KEY`), a cached one-hour Drive access token, the vault's folder ids, the last run, the SHA-256 of the current run's ticket (never the ticket itself), daily counters and push subscriptions; plus the allowlist. Rate-limit counters are kept in memory only, never in KV. Never note content: the last run's report (its summary and the names of the files it processed) is the only trace of it.
5. **What leaves the Worker:** to the app, an `HttpOnly; Secure; SameSite=Lax` session cookie and a one-hour Drive access token (never the refresh token). The session is a signed token naming only the user id, a random session id, the user's session generation and when it was signed: every sign-in issues a new one, it lasts at most 30 days from sign-in (never extended), and every cookie route rejects it (401 `session_expired`) once it is older than that or older than the user's last "Sign out everywhere" (`POST /auth/logout-all` bumps the generation in `sessiongen:<id>`); deleting the account writes a `deleted:<id>` tombstone and removes the user record, so every cookie stops working (401 `unauthenticated`), and revokes the refresh token at Google, best effort, logging only an error code on failure; after a rejected sign-in, an `HttpOnly; Secure; SameSite=Lax` `bower_not_invited` cookie holding only the address, AES-GCM encrypted inside a signed token, for 5 minutes and cleared by the first `GET /me`; to GitHub, a dispatch naming only the user id and that run's ticket; to push services, an encrypted notification.
6. **What the runner sees:** with its run's ticket, one vault's folder ids, a one-hour Drive access token and, for users who set one, their Claude API key. It keeps nothing after the run and logs no file names, summaries or tokens. **No job that runs the agent holds `BOWER_API_KEY`** (issue #259): for every run (a Tidy up press, or each vault's weekly health check), the Worker mints a random 32-byte ticket, keeps only its SHA-256, and sends the ticket in the `repository_dispatch`. `GET /runner/vaults/:id` and `POST /runner/vaults/:id/status` accept a ticket for its own vault and its own kind of run only, until the run reports `done` or `failed` (then it is retired), a newer run of the same kind replaces it, or 55 min pass. So code running inside a job (the agent, a compromised download or package) can reach that one vault for that one run, and no other. `BOWER_API_KEY` stays in the instance repo for the weekly lint's `dispatch` job alone, which only asks the Worker to start the health checks and never runs the agent. The real blast radius is therefore the instance repo itself: someone who can change its workflows can write a job that reads `BOWER_API_KEY` and has the Worker dispatch a ticketed run of every vault into it, which reaches every user's Drive; guard the instance repo like the Worker's secrets. While the transition flag `RUNNER_ACCEPT_LEGACY_KEY=1` is set on the Worker, `BOWER_API_KEY` also works on every vault's runner routes, as before; it is off by default (`docs/runbook.md`, "Upgrading to run tickets"). The model itself (`claude -p`, `agent/run.sh`) sees less than the shell that runs it: it starts under `env -i` with an explicit allow-list (`HOME`, `PATH`, `LANG`, `LC_ALL`, `TMPDIR`, `TERM`, `CI`/`GITHUB_ACTIONS` when set, and only the model credential), so a prompt-injected instruction that reaches the model anyway — a note in `0-Inbox/` or `Clippings/` is untrusted text — cannot read the Drive token, the run ticket or any other `BOWER_*`/`RCLONE_CONFIG_*` value out of its own process. Only the surrounding shell, which does the sync down, the sync up and the status report, holds those. Nor can the model read them from around its process (#258): the workflows hand the run ticket and the other `BOWER_*` settings to `run.sh` in a file (`$RUNNER_TEMP/bower-secrets`, mode 600), which it reads into unexported shell variables and deletes before anything else runs, so the initial environment of the shell that starts the model, readable in `/proc/<pid>/environ` and not cleaned by `env -i`, holds only the model credential and harmless variables; the Worker's answer (the Drive token and the user's API key) is read into variables and its file deleted at once, before the agent starts; and `agent/claude-settings.json` sets `permissions.blockReadsOutsideWorkingDirectories`, so file reads outside the vault (the work dir around it, the runner's home with its tool caches, `/tmp`) are refused, and also denies `Read` (which covers `Glob` and `Grep`) on `/proc`, `/etc`, `/root` and `..`. **The model credential is the exception, and it cannot be avoided:** `claude` needs `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY` in its own environment to call the model, so a prompt-injected note, or the owner of any vault through their own instruction note, can have the agent read it and write it into a note that is uploaded to that user's Drive. With the operator's credential running every user's jobs, any user of the instance can take it. For households whose members do not trust each other with it, prefer per-user API keys to the operator's OAuth token: each user sets **Use my own Claude API key** in Settings, which replaces the operator's credential for their runs, so the agent only ever holds the key of the user whose notes it is working on; and since the operator's credential, when set, is still in the job's environment on such a run, the operator leaves it unset in the instance repo (a user without their own key then gets `no Claude credentials`). Nor does the model get a tool that can send anything out: `Bash` is limited to `mv`, `mkdir` and `ls` (no `pandoc`, which takes a URL as input, and no `cp`, which can copy `/proc/self/environ` or any other runner file into the vault), and `WebSearch`, `WebFetch`, `curl` and `wget` are denied. Word, OpenDocument, HTML, EPUB and RTF files are converted to Markdown by `run.sh` before the model starts, with `pandoc --sandbox` (one input file, no other file, no URL). The one way a run reaches the network is the instance opting in with `BOWER_ALLOW_WEB=1`, which gives the model `WebSearch` and `WebFetch` back (`curl` and `wget` stay denied); a prompt-injected note can then send vault content to a third party.
   - **Set aside, and say so** (`agent/scan.sh`, pure, tested with fixtures in `agent/test/scan.test.sh`). Before Claude reads anything, a best-effort pre-scan looks over every pending text file in `0-Inbox/` and `Clippings/` (`.md`, `.txt`, `.html`, `.htm`, `.csv`, `.json`, `.eml`, including a converted document's Markdown sibling; `Processed/` and `Quarantine/` themselves are skipped) for patterns that read like instructions aimed at an assistant, case-insensitive: imperatives ("ignore all/any/the previous/prior/above instructions", "you are now", "system prompt", "as an AI"), role markers (`<|im_start|>`, a line starting `### Instruction` or `Assistant:`), an HTML comment or a `display:none`/`hidden` element whose own line carries one of those imperatives, zero-width or bidi control characters, and a run of more than 200 base64-alphabet characters. A flagged file is moved to `0-Inbox/Quarantine/` (a known root, so it is uploaded and its original path deleted like any other processed one) before `claude -p` starts, so the model never sees it, and is dropped from the pending list so it is never counted as processed; `0-Inbox/Quarantine/*` stays excluded from the pending list on every later run too, so a quarantined file is reported once, the run that quarantines it, and never becomes pending or processed again (issue #264). Reported as `quarantined`, a path only; the log carries only the count. Detection is best-effort, so the heuristics stay narrow: a false positive costs the user one manual move of the file back out of `Quarantine/` in Drive.
   - **Nothing persists from one run to the next** (`agent/run.sh`, `agent/claude-settings.json`). The protected paths are `CLAUDE.md` (the rulebook, and a `CLAUDE.md` at any depth, which Claude Code loads as memory), `README.md`, `.claude/**` and `.obsidian/**`: a prompt-injected note that rewrote them could plant instructions for every later run. The permission policy comes from the instance repo: `agent/claude-settings.json` replaces the vault's `.claude/settings.json` before every run (the vault's own copy and `.claude/settings.local.json` are ignored) and denies `Write`, `Edit` and `MultiEdit` on the protected paths and `Bash` commands whose arguments contain `://`. After the run, an audit compares the local copy with the manifest taken before it: `.claude/` and `.obsidian/` are never uploaded, every new or changed file outside the known roots (the PARA folders, `0-Inbox/`, `Clippings/`, `Answers/`, `Rules.md`, `About-Me.md`, `index.md`, `log.md`, `Lint Report.md`; so `CLAUDE.md` and `README.md` too) is reverted and not uploaded, and so is, inside them, any new or changed file named `CLAUDE.md`, at any depth; a run that changes more than `BOWER_MAX_CHANGES` files (default 200) is reverted entirely. Each revert is listed, as a path only, in the report's `refused`. The owner's own rules live in `Rules.md`, which the rulebook includes with the last word, so the rulebook itself never needs to change during a run; and because `Rules.md` is read with that authority by every later run, it may change only in an ingest whose agent was given an instruction note the app wrote (listed by Drive and not flagged by the pre-scan, point 6 under "Controls" below). In any other run, a lint included, a change to `Rules.md` is put back from the pre-run copy and reported in `refused`, so one injected note cannot plant a standing "rule" in an ordinary ingest (#263, finding M4 of `docs/security-review-2026-09-28.md`). New domain tags go to `log.md`, not `Rules.md`. `About-Me.md` stays writable in every run (Ingest step 7).
7. **Browsers:** only `APP_ORIGIN` may call the Worker with the cookie. CORS allows that origin alone, and state-changing session routes also check `Origin` (or `Referer`) against it, so another site cannot act on a signed-in user's behalf.
8. **Abuse:** every cookie route shares a generic per-IP rate limit, and the public entry points that cost something (`GET /auth/callback`, `POST /process`) also have a strict one; `POST /process` also has the per-user daily quota. Request bodies are capped at 64 KB and must be JSON, and the client's request id is bounded.
9. **The Google Picker API key** (`VITE_GOOGLE_API_KEY`, #53) is public by design: it is baked into the built app's JS, readable by anyone. It grants no access on its own — the Picker still uses the signed-in user's own Drive access token for the actual listing — and is restricted, in the Google Cloud Console, to the Picker API and to the app's origin (HTTP referrer), so it is useless if copied elsewhere.

### Same-site deployment

The session cookie stays `SameSite=Lax`, so the app and the Worker **must share a registrable domain**: for example `app.example.com` and `api.example.com`, or both on `localhost` when developing. The default `*.pages.dev` and `*.workers.dev` hostnames are on the public suffix list, so the app's calls to the Worker would be cross-site and the browser would not send the cookie. The alternative, `SameSite=None`, was rejected: it makes the cookie ride along on every cross-site request, and the CSRF check would become the only line of defence instead of the second.

## Checklist

- [x] CORS: only `APP_ORIGIN`, credentials allowed, methods `GET, POST, PATCH, DELETE, OPTIONS`, headers `Content-Type, Authorization, X-Request-Id`, `X-Request-Id` exposed; preflights answered (`api/src/security.ts`, `appCors`).
- [x] CSRF: `POST /process`, `POST /vault`, `PATCH /settings`, `DELETE /me`, `POST /auth/logout`, `POST /auth/logout-all`, `POST` and `DELETE /push/subscribe` require `Origin` (or, without it, the `Referer`'s origin) to equal `APP_ORIGIN`, else 403 `forbidden` (`requireSameOrigin`). Runner and admin routes (bearer keys, no cookie) and `GET` routes are exempt.
- [x] Session cookie `SameSite=Lax`, `HttpOnly`, `Secure`; app and API on one registrable domain (see above and `docs/runbook.md`).
- [x] Sessions (`api/src/auth.ts`, `api/src/session.ts`): a new session on every sign-in; an absolute lifetime of 30 days from sign-in (`iat`), with no sliding refresh; a per-user session generation in the claims, checked on every cookie route, so Settings → Sign out everywhere (`POST /auth/logout-all`) and account deletion end every session on every device. Revocation state lives in its own keys, never in the user record other routes rewrite: `sessiongen:<id>` (written only by logout-all) and a `deleted:<id>` tombstone (written by `DELETE /me` and operator removal, kept for good, checked first). Routes change the user record only through `updateUser`, which re-reads it and merges just their own fields, so a request holding an older copy (a stolen cookie calling `PATCH /settings` from another location) cannot lower the generation or re-create a deleted account; a sign-in after a deletion creates a new account with a new id. **Propagation window:** Workers KV is eventually consistent, so another location can read a revocation up to about 60 s late; a revoked cookie may keep working there for that long, and no longer. A rejected cookie is cleared. `DELETE /me` revokes the Google refresh token (`https://oauth2.googleapis.com/revoke`) before deleting; a failed revoke is logged as its error code only and does not block deletion.
- [x] Rate limit (strict): at most 30 requests in any 60 seconds on `GET /auth/callback`, per client IP, and on `POST /process`, per signed-in user, else 429 `rate_limited` with `Retry-After` (`rateLimit`). Counted only once a request could be legitimate: the callback first verifies the `bower_oauth` cookie (an HMAC, no KV) and its state, `POST /process` first runs the same-origin check and the session check, so a request without a valid cookie or session is refused (400, 403 or 401) before it is counted. In memory, like the generic limit (a second sliding window, `strictWindow`, at most 10,000 keys, best-effort per isolate), so it costs no KV write: a flood of requests cannot spend the free tier's 1,000 daily KV writes and take the instance down (#260, finding M1 of `docs/security-review-2026-09-28.md`). Covered by `api/test/security.test.ts`, and by handler tests asserting that an unauthenticated `POST /process` and a callback without a valid OAuth cookie write nothing to KV.
- [x] Generic rate limit: 120 requests per client IP in any 60 seconds across every cookie route (`/auth/*`, `/me`, `/drive/token`, `/settings`, `/vault`, `/process`, `/status`, `/push/subscribe`), else 429 `rate_limited` with `Retry-After` (`genericRateLimit`, mounted in `api/src/index.ts` before the strict limits). **Best-effort per isolate:** an in-memory sliding window (a `Map` from IP to request timestamps, pruned on each call, at most 10,000 IPs, least recently seen evicted first), so it costs no KV write; each Cloudflare isolate counts on its own and forgets on eviction, so a client spread over several isolates gets more. Nothing in it can fail, so it never blocks a request by error. The strict limits work the same way. One Home load is 3 calls (`/me`, `/status`, `/drive/token`); Tidy up is 1 `POST /process`, then 1 `GET /status` every 5 seconds while it runs (12 a minute), so the busiest minute of normal use is about 16.
- [x] Body size: 64 KB at most on every route, else 413 `payload_too_large`, before any handler parses the body (`limitBody`: `Content-Length` when sent, else a counted streamed read).
- [x] Content type: a write (`POST`, `PUT`, `PATCH`, `DELETE`) that carries a body must be `application/json`, else 415 `unsupported_media_type` (`requireJsonBody`). The writes without a body (`POST /auth/logout`, `POST /auth/logout-all`, `POST /process`, `DELETE /me`, `DELETE /admin/allow/:email`) are not checked.
- [x] Request id: a client `x-request-id` is kept only if it matches `^[A-Za-z0-9._-]{1,64}$`, else replaced by a UUID; never echoed or logged raw (`requestId`).
- [x] Headers on every response, errors included: `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`, `Content-Security-Policy: frame-ancestors 'none'` (`securityHeaders`).
- [x] App response headers (`app/public/_headers`, Cloudflare Pages): `Content-Security-Policy` (`script-src 'self'`, no `'unsafe-inline'` — see below for `style-src`; `connect-src` the API origin and `www.googleapis.com`; `img-src 'self' data: blob: *.googleusercontent.com`, Google's image host, for the account picture and a file's Drive thumbnail; `frame-ancestors 'none'`; `object-src 'none'`; `base-uri 'self'`; `form-action 'self'`; `worker-src 'self'` for the Workbox service worker), `Strict-Transport-Security` with preload, `X-Frame-Options: DENY`, `Permissions-Policy` denying camera, microphone and geolocation, `Referrer-Policy: strict-origin-when-cross-origin` (the origin only, never the path or query — the Worker's own responses keep `no-referrer`; the Google Picker API key is restricted by HTTP referrer, and the app's origin alone satisfies that check, which `no-referrer` would not). Generated at build time (`app/scripts/generate-headers.mjs`, run from `pnpm -C app build`) from `VITE_API_URL` (`connect-src`) and, only when set, `VITE_GOOGLE_API_KEY` (adds `https://apis.google.com` — its loader script — to `script-src`, and both that and `https://docs.google.com` — the Picker's own dialog, an iframe — to `frame-src`). `VITE_API_URL` unset (a plain `pnpm build`, CI's dry run) warns and leaves `connect-src` at `'self'` alone, matching the app's own same-origin fallback when the variable isn't set (`app/src/api.ts`); a value that's set but not a URL fails the build rather than shipping a placeholder. The wildcard `Access-Control-Allow-Origin: *` header that Cloudflare Pages adds by default is removed by the `_headers` file, since the app is purely static and never serves cross-origin data. `style-src` needs `'unsafe-inline'`: a handful of components (`tree.tsx`, `working-sheet.tsx`, `add.tsx`, `onboarding.tsx`) set a dynamic inline `style` attribute (row indent, progress width, animation delay) that CSP treats like an inline stylesheet; nothing in the built output uses an inline `<script>`. Target: **A** on securityheaders.com (`docs/runbook.md` § Security headers check).
- [x] Secret hygiene: `api/test/log-hygiene.test.ts` fails if any `console.*` call in `api/src/` passes or interpolates a variable named like a token, secret, key, email, refresh token or cookie. No violation was found when it was added.
- [x] CI supply chain: every `uses:` in `.github/workflows/ci.yml` and the instance workflows (`agent/workflows/ingest.yml`, `lint.yml`) pinned to a full commit SHA, version in a comment; `pull_request` and `push` runs gated by a `supply-chain` job (`pnpm audit --audit-level=high`, gitleaks); `permissions: contents: read` at the top of `ci.yml`, widened per job only where needed (the `supply-chain` job's PR comments); Dependabot (`.github/dependabot.yml`) weekly for npm (grouped minor/patch) and GitHub Actions.
- [x] Note rendering (#188): see below.
- [x] Key rotation: `SESSION_SECRET` supports a grace window through the optional `SESSION_SECRET_PREVIOUS` secret — `verifySession` (`api/src/session.ts`) tries the current secret, then the previous one, so a rotation doesn't have to sign every user out at once; tokens are always signed with the current secret only. Cadence and the step-by-step procedure for this and the other Worker secrets are in `docs/runbook.md`, "Hardening your instance".
- [x] Runner protected paths: permission policy from the instance repo (`agent/claude-settings.json`), post-run audit with known roots and `BOWER_MAX_CHANGES` in `agent/run.sh`; covered by `agent/test/smoke.sh`.
- [ ] Prompt injection: red-team corpus (`agent/test/redteam/`) run once against a real model, outcome table filled in below. See "Prompt injection".
- [x] Runner pre-scan: `agent/scan.sh` flags injection-shaped pending files and `agent/run.sh` quarantines them before the agent runs; covered by `agent/test/scan.test.sh` and `agent/test/smoke.sh`.
- [x] Web Share Target (#262/M3): the service worker's `POST /add` handler stores a share only when `Sec-Fetch-Site: none` (the OS share sheet, not a cross-site page's own `FormData` POST), and shared files land in the Add queue as waiting cards, uploaded only once the user taps "Add to Bower" (`app/src/share-target.ts`, `isTrustedShareRequest`; `app/src/sw.ts`).
- [x] This threat model.

## Prompt injection

### Threat model

Everything a run reads from `0-Inbox/` and `Clippings/` is untrusted text: a clipped web page, a forwarded document, a note added straight to Drive by someone other than the owner. Any of it can carry text aimed at the model rather than at the reader - "ignore your instructions and...", a hidden `<div>`, a base64 blob, or a file name or a frontmatter field written as if it were a command - and the model may comply. Detecting every such attempt is not the defence (the pre-scan below is explicitly best-effort); making compliance harmless is.

### Controls

1. **Pre-scan and quarantine** (`agent/scan.sh`, runs before Claude, pure and unit-tested). Every new file in `0-Inbox/` and `Clippings/` is checked against a narrow set of heuristics - imperatives aimed at an assistant, role markers, HTML comments or hidden elements holding one, zero-width or bidi control characters, long base64 blobs - and a match moves the file to `0-Inbox/Quarantine/` before the model ever sees it, listed as `quarantined` in the run's report. The agent is told to leave `Quarantine/` alone; the app tells the user what was set aside.
2. **Minimal environment** (`run.sh`; see "What the runner sees" above). The model's own process never holds the Drive token, the run ticket or any `RCLONE_CONFIG_*` value - only the model credential and a handful of harmless variables - and neither does its parent's `/proc` entry, the directory around the vault or anything the read policy lets it open. A prompt-injected instruction that reaches the model anyway has nothing to steal but the model credential itself.
3. **No network-capable tool by default.** `WebSearch`, `WebFetch`, `curl` and `wget` are denied; `Bash` is limited to `mv`, `mkdir` and `ls` (no `pandoc`, which takes a URL as input, and no `cp`, which could copy a runner file into the vault). Documents are converted to Markdown by `run.sh` itself, before the model starts. `BOWER_ALLOW_WEB=1` is the one, explicit opt-in that changes this.
4. **Protected paths and the post-run audit** (`agent/claude-settings.json`, `run.sh`). `CLAUDE.md` at any depth (`**/CLAUDE.md`), `README.md`, `.claude/**` and `.obsidian/**` cannot be written or edited by policy, and anything that reaches them anyway (an `mv`) is reverted after the run by comparing against the pre-run manifest; so is a change to `Rules.md` in a run whose agent was given no instruction note the app wrote; a run touching more than `BOWER_MAX_CHANGES` files (default 200) is reverted in full. Each revert is a `refused` entry in the report.
5. **The prompt itself** (`agent/prompts/ingest.md`). Told explicitly that note and clipping content is data to file, never instructions to follow, with one narrow exception: a file named exactly `Bower - <date> <time> <title>.md`, directly in `0-Inbox/`, with frontmatter `tags: [instruction]` and `via: app` - the only shape the app itself ever produces - and listed by the runner as written by the app. A file name alone, or a frontmatter field alone, is never enough.
6. **Instruction notes are checked for origin** (`agent/run.sh`, `app/src/drive.ts`). Name and frontmatter can be copied by anything that lands in `0-Inbox/`, so they are not proof that the app wrote a note. The app marks every instruction note it writes from Tell Bower with the Drive file property `appProperties: { bower: "instruction" }`, which Drive keeps private to the app's own OAuth client: nothing uploaded through Add, clipped, or dropped into the folder by hand carries it, and a copy through "Add from your Drive" clears it. Before the pre-scan, with the Drive token still in the shell and Claude not yet started, the runner lists the inbox files that carry it (one `files.list` call) into a private file outside the vault; every `Bower - *.md` directly in `0-Inbox/` that is not listed is quarantined like a pre-scan hit. A failed listing trusts none of them: every such note is quarantined. The log carries counts only.

None of these depend on the model reliably resisting a crafted note; each fixture below is designed to stay harmless even when it does not.

### Running it

CI cannot run a real model, so this is manual, done by the lead once per release, on the owner's own instance:

1. Create a throwaway folder in the owner's Drive - a fresh vault, not a real one - and note its id.
2. Copy every fixture file under `agent/test/redteam/*/` into that vault's `0-Inbox/` (flat is fine; the fixture folders are only for organising this corpus in the repo).
3. Trigger one ingest run for that vault: press Tidy up in the app, signed in with that folder as the Bower folder (a run needs the ticket the Worker's dispatch carries, so there is no manual trigger in the instance repo).

## Note rendering

A note is untrusted HTML as far as the app is concerned: the agent files web pages from `Clippings/` and `0-Inbox/`, and anything in the Bower folder can be edited outside the app. The app renders notes with `marked` and sanitizes the result with DOMPurify (`app/src/markdown/render.ts`); embeds are filled in afterwards (`app/src/markdown/hydrate-embeds.ts`). The profile:

- **Tags and attributes:** a fixed allowlist of text, list, table, heading, code, link and image tags (`ALLOWED_TAGS`), plus read-only checkboxes (a hook forces `type="checkbox" disabled`). No SVG or MathML (also in `FORBID_TAGS`), no `script`, `style`, `iframe`, `form`, `object`. No event handlers, no `style` attribute, no `data-*` except the two embed placeholders, every `id` prefixed `user-content-` against DOM clobbering.
- **URLs:** `href` and `src` must be `http(s):`, `mailto:`, `/note/<id>` (optionally `#heading`; nothing with `..` that could reach another path of the app) or `#heading`. `javascript:`, `vbscript:` and every other scheme are dropped, however they are spelled (case, entities, whitespace).
- **`data:` URLs:** only as the `src` of an `img`, and only base64 PNG, JPEG, GIF, WebP, AVIF or BMP, because pasted and clipped Obsidian notes carry inline images that way. Never SVG (a document that can carry script if opened on its own), never on a link.
- **External links** (`http(s):`) always get `target="_blank" rel="noopener noreferrer"` from a hook, whatever the note wrote; so do the app's own links to files in Drive. Links inside the app and `mailto:` get neither.
- **Remote images** (`<img src="https://...">`) pass the sanitizer but not the CSP (`img-src 'self' data: blob: https://*.googleusercontent.com`), so a note cannot make the app fetch an image from an arbitrary server (a tracking pixel). Google's image host is admitted for Drive's thumbnails: a file's screen shows a PDF's first page from its `thumbnailLink` (#350).
- **Attachments:** images in the Bower folder are fetched with the user's Drive token and shown through `blob:` object URLs, revoked when the note closes. An object URL is only ever created with an image MIME type (the bytes' own, Drive's, or the one the extension implies), so an HTML file named `photo.png` cannot become a same-origin page if someone opens the image on its own. Images over 10 MiB are not loaded inline; the reader gets a link to Drive. PDFs and every other file are links that open in Google Drive in a new tab: no PDF is shown inside the app, so there is no frame to sandbox (one would also need `frame-src blob:`, which the CSP does not allow).
- **Transclusion** (`![[Other note]]`): nests at most 3 deep, at most 20 notes per note in all, never a note longer than 200,000 characters, and never a note inside itself within one chain of embeds (a loop stops at the first repeat). Past a cap the embed stays a plain link to the note. Each transcluded body goes through the same sanitizer.
- **Cache:** image bytes are cached in IndexedDB under a 50 MB least-recently-used cap; updates to the LRU list are serialised so concurrent image loads cannot escape the cap (#133).

## Dynamic scan (ZAP baseline)

`.github/workflows/zap.yml` is a manually dispatched workflow (**Actions → ZAP baseline → Run workflow**) that runs the [OWASP ZAP](https://www.zaproxy.org/) baseline scan against a deployed instance, on demand: it is not part of CI and never runs on a push or a PR. Give it the two URLs to scan (`app_url`, the app's origin; `api_url`, the Worker's origin), both `https://`; a first step in the workflow rejects anything else. It then runs the scan twice, app first, then API (`zaproxy/action-baseline`, pinned by commit SHA), and uploads each run's report as a workflow artifact (`zap-baseline-app`, `zap-baseline-api`) — nothing is posted back to the repo as an issue.

`.github/zap-rules.tsv` allowlists findings that are expected given this app's shape (a client-routed SPA in front of a JSON API) rather than defects; each row carries a one-line reason. A scan fails the workflow (`fail_action: true`) on anything not in that file. When a run fails:

- **Real finding** — fix it (open an issue if it needs its own PR).
- **Expected given the architecture, not a defect** — add a row to `.github/zap-rules.tsv` with a reason, same format as the existing rows.
